# Конвенції коду: Next.js + NestJS monorepo

Документ описує правила, обов'язкові для всього коду в репозиторії.

**Головний принцип: правило, яке не перевіряється автоматично — це побажання, а не правило.**
Кожен розділ має колонку «Як enforce». Якщо правило неможливо перевірити лінтером, типами
або code review checklist — його треба або переформулювати, або видалити.

**Другий принцип: код оптимізується під читання і видалення, не під написання.**
Найдорожча операція в проєкті — не «додати фічу», а «зрозуміти чужий модуль через 8 місяців»
і «безпечно видалити те, що більше не потрібно».

## 0. Базові налаштування (без них решта правил не працює)

### 0.1 TypeScript

`tsconfig.base.json` в корені монорепо, всі пакети наслідують:

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,      // arr[0] має тип T | undefined
    "exactOptionalPropertyTypes": true,     // { a?: string } !== { a: string | undefined }
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "verbatimModuleSyntax": true,           // import type обов'язковий для типів
    "isolatedModules": true
  }
}
```

**`any` заборонений.** Якщо тип справді невідомий — `unknown` + звуження через zod або type guard.
`as` дозволений тільки в двох випадках: `as const` і звуження після runtime-перевірки. Будь-який
інший `as` вимагає коментаря `// eslint-disable-next-line ... -- причина`.

`@ts-ignore` заборонений повністю. `@ts-expect-error` дозволений тільки з поясненням в тому ж рядку.

### 0.2 Обов'язковий тулінг

| Інструмент | Навіщо |
|---|---|
| ESLint (flat config) + `typescript-eslint` (type-aware) | правила нижче |
| `eslint-plugin-boundaries` або `dependency-cruiser` | архітектурні межі між шарами |
| `eslint-plugin-import` (`no-cycle`, `no-restricted-paths`) | цикли й заборонені імпорти |
| Prettier | форматування — жодних дискусій про стиль у PR |
| `knip` | мертвий код, невикористані експорти й залежності |
| `lint-staged` + `husky` | нічого не потрапляє в комміт непроходженим |
| `vitest` (web) / `jest` (api) | тести |
| CI: `typecheck` → `lint` → `test` → `build` | PR не мерджиться на червоному |

## Частина I. Next.js (apps/web)

### 1. Структура

**1.1 `app/` — це роутинг, а не місце для коду.**
У файлах `page.tsx`, `layout.tsx`, `route.ts` дозволено: читання params/searchParams, виклик
завантаження даних, композиція компонентів, метадані. Максимум ~50 рядків. Уся розмітка й логіка —
у компонентах фічі.

**1.2 Feature-first, а не type-first.**
Групуємо за доменом, не за технічним типом файлу.

```
src/
  app/                      # тільки роути
    (auth)/login/page.tsx
    catalog/[bookId]/page.tsx
  features/
    friends/
      components/
        FriendRow.tsx
        FriendsList.tsx
      hooks/use-friend-requests.ts
      api/friends.queries.ts
      model/friend.types.ts
      index.ts              # публічний інтерфейс фічі
    catalog/
    loans/
  components/ui/            # дизайн-система: Button, Input, Dialog — 0 бізнес-логіки
  lib/                      # cn(), fetcher, date helpers — 0 залежностей від фіч
```

**1.3 Правило публічного інтерфейсу.**
Фіча експортує назовні тільки те, що є в її `index.ts`, і тільки явними іменованими реекспортами:

```ts
// features/friends/index.ts
export { FriendsList } from './components/FriendsList'
export { FriendRow } from './components/FriendRow'
export type { Friend } from './model/friend.types'
```

Заборонено:
- `export *` (тихі колізії імен, непрозорий граф, зламаний автоімпорт);
- глобальний барел `@/components/index.ts` на весь проєкт;
- імпорт з чужої фічі глибше, ніж її `index.ts` (`@/features/loans/components/LoanCard` — помилка);
- імпорт фічі з `components/ui` або `lib` (залежність тільки в один бік).

Enforce: `eslint-plugin-boundaries` + `import/no-restricted-paths`.
Якщо в барелі більше ~20 експортів — фічу треба різати, а не барел.

**1.4 Default export — тільки там, де його вимагає фреймворк**
(`page.tsx`, `layout.tsx`, `error.tsx`, `loading.tsx`, `not-found.tsx`, `middleware/proxy`, конфіги).
Скрізь інде — named export. Причина: named-експорти рефакторяться перейменуванням, дефолтні —
розповзаються довільними іменами по кодовій базі.

**1.5 Одне ім'я скрізь.** Файл `FriendRow.tsx` → компонент `FriendRow` → експорт `FriendRow`.
Папки — `kebab-case`, файли компонентів — `PascalCase`, решта файлів — `kebab-case`
(`use-friend-requests.ts`, `friend.types.ts`).

### 2. Server / Client boundary — найважливіший розділ

**2.1 Server Component за замовчуванням.** `'use client'` додається тільки тоді, коли компоненту
реально потрібні: стан, ефекти, браузерні API, обробники подій, контекст.

**2.2 `'use client'` ставиться якнайнижче в дереві — на листках, не на гілках.**
Заборонено ставити `'use client'` у `layout.tsx` і `page.tsx`. Якщо сторінці потрібна
інтерактивність — виносимо інтерактивний шматок в окремий клієнтський компонент.

Погано:
```tsx
'use client'                      // ← вся сторінка поїхала в клієнтський бандл
export default function CatalogPage() { ... }
```

Добре:
```tsx
// page.tsx (server)
export default async function CatalogPage({ searchParams }) {
  const books = await getBooks(await searchParams)
  return <><CatalogSearch /><BookGrid books={books} /></>   // CatalogSearch — 'use client'
}
```

**2.3 Клієнтські й серверні модулі не змішуються в одному барелі.**
Імпорт одного символу транзитивно тягне сусідній модуль у контекст, де він падає
(`next/headers` у клієнті, `useState` на сервері). Якщо фіча має обидві сторони — два входи:
`index.ts` і `index.client.ts`.

**2.4 Маркуємо межу явно.** У пакетах: `server-only` в модулях з доступом до БД/секретів,
`client-only` в модулях з браузерними API. Це перетворює runtime-помилку на build-помилку.

**2.5 Пропси через межу мають бути серіалізовані.** Не передаємо в клієнтський компонент
функції (крім Server Actions), класи, `Date` без нормалізації, Prisma-моделі цілком.
Передаємо рівно ті поля, які потрібні для рендеру.

**2.6 Дані фетчаться на сервері.** `useEffect` + `fetch` для початкового завантаження заборонено.
Мутації — Server Actions або типізований клієнт до NestJS. Server Action **завжди** починається
з перевірки авторизації й валідації входу — це публічний HTTP-ендпоінт, а не приватна функція.

### 3. Правила самого компонента

**3.1 Один файл — один компонент.** Дрібні приватні підкомпоненти в тому ж файлі допустимі, поки
файл < 250 рядків. Далі — розділяємо.

**3.2 Пропси — окремий іменований тип, не інлайн.**

```tsx
type FriendRowProps = {
  friend: Friend
  onRemove?: (id: string) => void
}

export function FriendRow({ friend, onRemove }: FriendRowProps) { ... }
```

Заборонено: `React.FC` (нав'язує `children`, погано працює з generics), `any` в пропсах,
`{...props}` розкидання невідомого об'єкта (крім навмисного forwarding у `components/ui`).

**3.3 Максимум 3 булеві пропси.** Четвертий — сигнал, що це насправді кілька компонентів
або що потрібен `variant: 'compact' | 'full'`. Іменування: `isLoading`, `hasError`, `canEdit`.

**3.4 Prop drilling глибше 2 рівнів заборонений.** Виходи: композиція через `children`,
контекст фічі, або переміщення стану.

**3.5 Три стани обов'язкові.** Будь-який блок, що залежить від асинхронних даних, має явно
описані `loading`, `error`, `empty`. Відсутність empty-стану — це баг, а не дрібниця.

**3.6 Списки: стабільний `key`.** `key={index}` заборонений скрізь, де список може змінювати
порядок або довжину.

**3.7 `useEffect` — крайній засіб.** Дозволений тільки для синхронізації з зовнішньою системою:
підписки, таймери, DOM-API, аналітика. Заборонений для: обчислення похідного стану (це просто
змінна або `useMemo`), трансформації пропсів у стан, завантаження даних.

**3.8 Стан живе якнайближче до місця використання.** Порядок вибору:
локальний `useState` → URL (`searchParams`) → контекст фічі → глобальний стор.
Фільтри, пошук, пагінація, відкриті таби — **завжди в URL**. Це дає безкоштовно:
шеринг посилань, кнопку «назад», SSR і збереження стану після рефрешу.

**3.9 Серверний стан ≠ клієнтський стан.** Дані з API не кладуться в `useState`.
Для клієнтських запитів — TanStack Query (кеш, дедуплікація, retry, інвалідація).

**3.10 Стилі.** Tailwind + `cva` для варіантів + `cn()` для мержу класів. Заборонено:
магічні значення поза токенами дизайн-системи (`mt-[13px]`), інлайн `style` крім справді
динамічних обчислень (позиція, прогрес), умовні класи через конкатенацію рядків.

**3.11 Доступність — частина визначення «готово».** Інтерактивний елемент — це `<button>`
або `<a>`, не `<div onClick>`. Кожен інпут має `label`. Кожне зображення має `alt`.
Enforce: `eslint-plugin-jsx-a11y`.

### 4. Дані й типи

**4.1 Типи API живуть в одному місці** (`packages/shared`) і не дублюються вручну на фронті.
Ручне переписування DTO — гарантований дрейф між фронтом і бекендом.

**4.2 Валідація на межі.** Усе, що приходить ззовні (форми, `searchParams`, відповіді API,
вебхуки), парситься zod-схемою. Далі по коду ходить уже типізовані дані, а не `unknown`.

**4.3 Форми: React Hook Form + zod resolver.** Схема валідації одна для клієнта й сервера.

## Частина II. NestJS (apps/api)

### 5. Модулі й шари

**5.1 Один домен — один модуль.** Модуль інкапсулює свою доменну область і експортує тільки
сервіси, які реально потрібні іншим.

```
src/
  modules/
    loans/
      loans.module.ts
      loans.controller.ts
      loans.service.ts          # бізнес-логіка
      loans.repository.ts       # доступ до даних (Prisma)
      dto/create-loan.dto.ts
      dto/loan-response.dto.ts
      loans.service.spec.ts
  common/
    guards/ interceptors/ filters/ decorators/ pipes/
  infra/
    prisma/ redis/ mailer/
  config/
```

**5.2 Напрямок залежностей строгий:**
`controller → service → repository → prisma`.
Зворотні стрілки й перестрибування шарів заборонені. Контролер ніколи не бачить Prisma.
Enforce: `dependency-cruiser`.

**5.3 Циклічні залежності модулів заборонені.** `forwardRef()` — не рішення, а маркер помилки
в декомпозиції. Якщо він справді потрібен — над ним обов'язковий коментар з поясненням, чому
розділити не вийшло. Альтернатива: події (`EventEmitter`) або третій спільний модуль.

### 6. Контролери

**6.1 Контролер тонкий: HTTP in → DTO → виклик сервісу → response DTO out.**
Нуль бізнес-логіки, нуль звернень до БД, нуль `if`-ів про домен. Якщо в контролері з'явився
другий `if` — логіка йде в сервіс.

**6.2 `@Res()` заборонений** (ламає інтерцептори, серіалізацію й обробку помилок Nest).
Статус-код — через `@HttpCode()`, помилки — через винятки.

**6.3 Кожен ендпоінт має:** DTO входу, тип виходу, guard (або явний `@Public()`),
Swagger-декоратори (`@ApiOperation`, `@ApiResponse`), тест.
Ендпоінт без явного рішення про авторизацію — блокер на рев'ю.

**6.4 Версіонування з першого дня** (`/api/v1/...`). Додати пізніше дорожче, ніж закласти зараз.

### 7. DTO і серіалізація

**7.1 Глобальний `ValidationPipe` з жорсткими налаштуваннями:**

```ts
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,              // зрізає невідомі поля
  forbidNonWhitelisted: true,   // або взагалі падає на них
  transform: true,
  transformOptions: { enableImplicitConversion: false },
}))
```

**7.2 Prisma-модель ніколи не повертається клієнту напряму.** Це найпоширеніший спосіб злити
`passwordHash`, внутрішні прапорці або чужий email. Вихід — завжди явний response DTO
(або `@Expose()` + `ClassSerializerInterceptor` з `excludeAll` за замовчуванням).

**7.3 DTO входу ≠ сутність домену ≠ DTO виходу.** Три різні типи, навіть якщо сьогодні вони
збігаються полями. Вони розійдуться на третьому спринті.

**7.4 Пагінація й фільтри — теж DTO** з обмеженнями (`@Max(100)` на `limit`).
Ендпоінт, що повертає необмежений список, — це DoS, який чекає свого моменту.

### 8. Сервіси й бізнес-логіка

**8.1 Сервіс не знає про HTTP.** Він кидає доменні винятки (`BookNotAvailableError`,
`LoanAlreadyReturnedError`), а не `NotFoundException`. Мапінг доменних помилок у HTTP-коди —
в одному глобальному `ExceptionFilter`. Це те, що дозволяє потім винести домен у воркер,
крон або чергу без переписування.

**8.2 `throw new Error('...')` заборонений.** Тільки типізовані доменні винятки — інакше
неможливо ні відрізнити очікувану помилку від багу, ні коректно її залогувати.

**8.3 Стан-машина описується явно.** Для переходів статусів (у нас — 7 станів позики)
має бути одна таблиця/мапа дозволених переходів і одна функція, що їх перевіряє.
Розкидані по коду `if (status === 'PENDING')` — заборонені.

**8.4 Кожна багатокрокова зміна даних — в транзакції.** «Створити позику + зменшити кількість
доступних примірників + записати історію» — це один `$transaction`, не три запити підряд.

**8.5 Ідемпотентність для небезпечних операцій.** Повторний POST не має створювати другу позику.

**8.6 Ніяких запитів у циклі (N+1).** Prisma: `include`/`select` або batching.
У код-рев'ю `await` всередині `for` по масиву з БД — автоматичний блокер.

**8.7 `select` замість `include` всюди, де можна.** Забирай тільки потрібні поля — це і
продуктивність, і захист від випадкового витоку полів у відповідь.

### 9. Інфраструктурні правила

**9.1 `process.env` читається рівно в одному місці** — у конфіг-модулі, де вся схема
env валідується zod-ом **на старті застосунку**. Немає змінної — процес падає одразу,
а не через тиждень у продакшені о третій ночі.

**9.2 `new PrismaClient()` створюється один раз** у `PrismaService`. Скрізь інде — інжекція.

**9.3 Логи структуровані (JSON), з `requestId`.** Заборонено логувати: паролі, токени, ключі,
повні тіла запитів з PII. `console.log` у продакшн-коді — блокер.

**9.4 Крос-cutting логіка — в guards / interceptors / filters, не в сервісах.**
Авторизація, rate limiting, кешування, таймінги, трансформація відповіді.

**9.5 Кожна зміна схеми — міграція в репозиторії.** `prisma db push` дозволений лише
на локальній машині; ніколи в спільному чи продакшн-середовищі.

**9.6 Health-check і graceful shutdown** налаштовані до першого деплою, не після першого падіння.

## Частина III. Спільне для монорепо

### 10. Межі пакетів

- `packages/shared` містить типи, zod-схеми, константи, чисті утиліти.
  **Нуль залежностей від React, Nest, Prisma-клієнта і будь-чого середовище-специфічного.**
- Напрямок залежностей: `apps/*` → `packages/*`. Ніколи навпаки. Ніколи `apps/web` → `apps/api`.
- Кожен пакет має `"sideEffects": false`, якщо він справді без сайд-ефектів — інакше
  tree-shaking не працює.

### 11. Іменування

| Що | Як | Приклад |
|---|---|---|
| Компонент | PascalCase, іменник | `FriendRow` |
| Хук | `use` + дієслово/іменник | `useFriendRequests` |
| Булеве | `is` / `has` / `can` / `should` | `isPending`, `canBorrow` |
| Обробник (проп) | `on` + подія | `onApprove` |
| Обробник (реалізація) | `handle` + подія | `handleApprove` |
| Сервісний метод | дієслово + домен | `approveLoanRequest` |
| Тип | без префіксів `I`/`T` | `Loan`, не `ILoan` |
| Константа | SCREAMING_SNAKE | `MAX_ACTIVE_LOANS` |

Магічні числа й рядки заборонені. `if (loans.length >= 5)` → `MAX_ACTIVE_LOANS`.

### 12. Тести

**12.1 Обов'язково покриті:** бізнес-правила домену (переходи станів, ліміти, розрахунок
рейтингу), кожен публічний ендпоінт (e2e, happy path + 401/403 + валідація),
кожен нетривіальний хук.

**12.2 Не тестуємо:** розмітку, дрібні презентаційні компоненти, реалізацію фреймворку.

**12.3 Тест на баг перед фіксом.** Регресія без тесту повернеться.

**12.4 Ім'я тесту описує правило, а не метод:**
`відхиляє запит, якщо в користувача вже 5 активних позик`.

### 13. Git і review

- Conventional Commits (`feat(loans): ...`, `fix(web): ...`) — з них генерується changelog.
- PR ≤ ~400 рядків диффа. Більше — рев'ю стає формальністю, а не рев'ю.
- Один PR — одна зміна. Рефакторинг і фіча в одному PR — окремо не рев'юяться.
- CI зелений — обов'язкова умова мержу, без винятків «зафіксимо потім».
- TODO без issue-посилання заборонений: `// TODO(#142): ...`.

### 14. Hard bans (короткий список)

1. `any`, `@ts-ignore`
2. `export *`
3. Глобальний барел на всі компоненти
4. `'use client'` у `layout.tsx` / `page.tsx`
5. Prisma-модель у HTTP-відповіді
6. Бізнес-логіка в контролері
7. `process.env` поза конфіг-модулем
8. `console.log` у продакшн-коді
9. Дані з API у `useState` + `useEffect`
10. Закоментований код у комміті (для цього є git)
11. Циклічні залежності
12. Ендпоінт без явного рішення про авторизацію

## Частина IV. Що видає якісний код рецензенту (тімліду, інтерв'юеру, клієнту)

Це не про правила, а про сигнали, які зчитуються за 5 хвилин перегляду репозиторію:

1. **Структура читається без пояснень.** З дерева папок видно, що робить застосунок, а не яким
   фреймворком написаний. `features/loans/` каже більше, ніж `components/ hooks/ utils/`.
2. **Межі явні.** Видно, де закінчується сервер і починається клієнт; де домен, а де транспорт.
3. **Помилки оброблені там, де вони виникають,** а не задавлені `try/catch` з порожнім тілом.
4. **Стани UI повні.** Loading, error, empty — не забуті. Це найшвидший спосіб відрізнити
   продакшн-код від демо.
5. **Немає закоментованого й мертвого коду.** `knip` у CI гарантує це автоматично.
6. **Типи описують домен, а не структуру JSON.** `LoanStatus` як union, а не `string`.
7. **README пояснює, як запустити за 3 команди,** і що робить проєкт.
   `ARCHITECTURE.md` пояснює, чому саме так, а не інакше — це найсильніший сигнал зрілості:
   видно, що рішення приймалися свідомо, а не накопичувалися.
8. **Комміти розповідають історію.** `fix stuff`, `wip`, `final2` — навпаки.
9. **Секрети ніде не лежать у репозиторії,** є `.env.example` з усіма ключами.
10. **Тести є там, де є ризик,** і їх немає там, де вони були б шумом. Це помітно одразу
    і читається як інженерна зрілість, а не як гонитва за відсотком покриття.
