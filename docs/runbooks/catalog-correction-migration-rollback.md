# Rollback/recovery runbook — Stage 8e-1 catalog correction schema

Стосується двох міграцій:

- `20260910231627_catalog_correction_audit_schema` — additive: `Work`/`Translation`/`Edition.revision`,
  `Translation.createdById`/`createdAt` (nullable), `WorkAuthor.position` (nullable), backфіл обох,
  таблиця `CatalogRevision`.
- `20260910231806_catalog_correction_audit_required` — робить `Translation.createdById` і
  `WorkAuthor.position` `NOT NULL`.

Обидві вже застосовані до локальної dev-бази (`pnpm db:deploy`). Цей документ описує, як безпечно
відкотити кожен окремий наслідок, а не як «відкотити ці два файли».

## Золоте правило: історія міграцій — append-only

Prisma зберігає в `_prisma_migrations` контрольну суму кожного застосованого `migration.sql` і звіряє
її при кожному `migrate deploy`/`migrate dev`. Якщо файл змінити ПІСЛЯ того, як його вже застосовано
хоч десь (локальна dev-база, CI, майбутній прод), той інструмент повідомляє, що міграцію змінено після
застосування, і відмовляється продовжувати на цьому оточенні. Точний текст/код помилки залежить від
версії Prisma CLI — не покладайся в автоматизації на конкретний P-код; сигнал, на який варто реагувати,
— сама відмова `migrate deploy`/`migrate dev`, а не її форматування.

Офіційного «полагодь одним махом» для цього стану немає. `prisma migrate resolve` призначений для
FAILED-міграцій (тих, що впали посеред застосування), а не для файлу, який ЗМІНИЛИ ПІСЛЯ успішного
застосування, — це інший випадок. Технічно можливо вручну підправити рядок у `_prisma_migrations`
(перерахувати й записати нову контрольну суму), але це:

- ручна, для кожного оточення окремо операція (dev, CI, прод — кожне зі своєю копією таблиці);
- легко помилитися й замаскувати справжню розбіжність, а не полагодити її;
- **не типовий, не рекомендований шлях**, а операція останньої інстанції, з задокументованим рішенням,
  чому саме вона, а не запобігання.

Тому: **ніколи не редагувати й не видаляти вже застосовані файли міграцій**, і не робити
`prisma migrate reset` на dev-базі як спосіб «скасувати». Будь-яка з дій нижче — це НОВА
forward-міграція (`prisma migrate dev --create-only --name <назва>` або вручну новий каталог у
`prisma/migrations/`), яка компенсує ефект, а не переписує те, що вже застосовано. Якщо колись
знадобиться змінити SQL самих двох міграцій вище — спочатку описати саме цей шлях (нова міграція,
а не правка), а не мовчки відредагувати файл.

## Автоматизований доказ (§A, §B і recovery нижче)

Три db-spec файли виконують сценарії цього runbook на окремих guarded scratch-БД
(`apps/api/test/db/migration-scratch.ts`, кожен зі своїм ключем) — не на спільній `_test` базі й не на
dev-базі. Вони частина штатного `pnpm test:db` / `./gate.sh`, тож ці твердження перевіряються при
кожному прогоні gate, а не лише один раз руками:

- `catalog-correction-rollback.db-spec.ts` (ключ `rollback`) — §A і §B: старий формат `INSERT` (без
  `position`/`createdById`, точно такий, який робив код ДО Stage 8e-1) падає з `not_null_violation`
  (`23502`) на required-міграції; SQL §A застосовується без помилок, відновлює здатність старого коду
  писати, і не чіпає жодного наявного рядка `Work` чи `CatalogRevision`.
- `catalog-correction-recovery.db-spec.ts` (ключ `recovery`) — §B recovery: справжня друга сесія
  відкриває транзакцію-писача й НЕ комітить її; recovery, запущений паралельно, доведено чекає (не
  падає, не проходить одразу) саме на цей коміт, і лише після нього починає виконуватися; тим часом
  ще одна, третя сесія намагається писати — і теж чекає, доки recovery не закомітить. Далі: ручний,
  неалфавітний порядок `position` переживає recovery недоторканим; рядок, доданий NULL під час вікна
  §A/§B, дописується ПІСЛЯ наявного максимуму, а не вставляється й не пересортовує решту;
  `CatalogRevision` і `Work.revision` не чіпаються; жодного NULL не лишається; required-міграція
  накочується знову без помилок; і насамкінець — **справжній згенерований `PrismaClient`** (не raw
  SQL) читає ці самі рядки без винятку. **`RECOVERY_SQL` у цьому тесті — той самий текст, що й у §B
  нижче, символ у символ.** Якщо колись розійдуться — файл застарілий, не runbook.

Сценарій C (§C) навмисно НЕ автоматизований — див. пояснення в його розділі.

## §A. Скасувати лише вимогу NOT NULL

**Коли:** щось поза цим застосунком (інший сервіс, ручний import-скрипт) усе ще пише
`Translation`/`WorkAuthor` без цих двох колонок, і потрібен час полагодити той писач, не втрачаючи
ні additive-схему, ні `CatalogRevision`.

Нова forward-міграція:

```sql
ALTER TABLE "Translation" ALTER COLUMN "createdById" DROP NOT NULL;
ALTER TABLE "WorkAuthor" ALTER COLUMN "position" DROP NOT NULL;
```

**Що це дає:**

- Схема повертається у стан «additive» (як одразу після першої з двох міграцій): нові рядки знову
  можуть мати `createdById`/`position = NULL`.
- Жодні наявні дані не втрачаються — ні `revision`, ні вже забекфілені `createdById`/`position`, ні
  `CatalogRevision`. Перевірено автоматизованим тестом вище.
- `schema.prisma` тут НЕ редагується: моделі `Translation`/`WorkAuthor` лишаються оголошені як
  обов'язкові поля (`createdById String`, `position Int`, без `?`) — SQL вище є запобіжним клапаном
  на рівні БД, а не новим довгостроковим рішенням «поле насправді nullable».

**Чого це НЕ дає — прочитати перед використанням.** §A знімає обмеження лише на рівні БД. Він
**НІЧОГО не робить безпечнішим для читання**: поточний (і будь-який пост-Stage-8e-1) Prisma Client
згенеровано зі схеми, де `position Int`/`createdById String` — НЕ `Int?`/`String?`. Коли цей клієнт
читає рядок із фактичним `NULL` у будь-якому з цих полів (`prisma.workAuthor.findMany()`,
`catalog.mapper.ts` → `toWorkAuthors`, який типізує `WorkAuthorRow.position` як `number`, не
`number | null`), десеріалізація падає — це НОВИЙ режим відмови, який `§A` сам по собі вводить, а не
усуває. `§A` розв'язує проблему ЗАПИСУ (старий/зовнішній код знову може писати), а не проблему
ЧИТАННЯ (поточний код читає ці ж рядки і ламається). Використовувати `§A` без плану, як швидко
прибрати NULL-рядки ДО того, як поточний код їх прочитає (recovery, крок 3 нижче, або обмеження
читання на час вікна), — самому створити інцидент замість того, щоб його уникнути.

## §B. Відкотити застосунок до версії ДО Stage 8e-1, лишивши схему вперед

**Коли:** новий код (байдуже, якого підетапу — 8e-1 сам по собі ще не додає жодного PATCH-ендпоінта,
але 8e-2/8e-3 додадуть) виявив баг, і треба перевикотити попередній образ застосунку, не чіпаючи БД.

**Це НЕБЕЗПЕЧНО без §A.** Старий `schema.prisma` (до Stage 8e-1) не мав полів
`Translation.createdById`/`WorkAuthor.position` узагалі — його згенерований Prisma Client ніколи не
підставляє їх у `INSERT`. Якщо required-міграція вже застосована (`NOT NULL`, без `DEFAULT`), кожен
`POST /works` (запис `WorkAuthor`) і кожен `POST /works/:id/translations` старого коду впаде на
`not_null_violation` — перевірено тим самим автоматизованим тестом.

**Порядок писачів і читачів — не лише «накотити SQL, потім задеплоїти».** §A знімає обмеження в БД,
але старий і поточний код НЕ можуть безпечно обслуговувати трафік одночасно (canary/rolling deploy)
у цьому вікні: поточний код падає на читанні NULL-рядка, який щойно міг записати старий. Послідовність:

1. **Зупинити писачів поточної версії** (або перевести деплой у режим, де жодна поточна репліка не
   приймає запити на запис каталогу) — щоб під час вікна не змішувалися дві версії, що по-різному
   розуміють ці колонки.
2. Застосувати forward-міграцію §A (`DROP NOT NULL` на обох колонках).
3. **Повний cutover, не canary**: викотити стару версію як ЄДИНУ, що обслуговує і записи, і читання
   зачеплених шляхів (`POST/GET /works`, `POST /works/:id/translations`) — жодна поточна репліка не
   повинна лишатися в цьому пулі, поки старий код може писати NULL-рядки, які вона прочитає.
4. Нові рядки, створені старим кодом у цьому вікні, матимуть `createdById`/`position = NULL`. Перш ніж
   знову викочувати код, що ЧИТАЄ ці поля як обов'язкові — **recovery** (не звичайний backfill, див.
   нижче): одна транзакція, яка сама зупиняє писачів каталогу на час своєї роботи (`LOCK TABLE`) і
   чекає завершення тих, що вже писали, замість покладатися, що оператор вручну зупинив усіх «старих і
   зовнішніх» писачів до її запуску.
5. Та сама транзакція відновлює `NOT NULL` ДО commit — немає вікна між «NULL заповнено» і «вимога
   знову діє», у яке міг би встрягнути новий писач: `LOCK TABLE` тримається аж до `COMMIT`.
6. **Лише ПІСЛЯ commit** — перевірити, що поточний `PrismaClient` читає зачеплені рядки без винятку
   (не лише «raw SQL каже нуль NULL» — round 2 цього документа вже показав, чому цього недостатньо).
   Тільки тоді відкривати трафік новій версії й, за потреби, накочувати required-міграцію знову
   (`recovery`, крок 5, уже зробив це в тій самій транзакції — цей крок лише про required-МІГРАЦІЮ як
   файл, якщо оператор хоче й формально позначити її застосованою).

### Recovery (кроки 4–5) — одна заблокована транзакція, НЕ повторний blanket backfill

**Не запускай повторно `BACKFILL:POSITION:*` з
`20260910231627_catalog_correction_audit_schema/migration.sql` як є.** Той запит рахує `position`
для КОЖНОГО рядка `WorkAuthor` заново, без `WHERE position IS NULL` — це було безпечно один раз, у
самій міграції, коли позиція була NULL буквально для всіх рядків одразу (ручного порядку ще не
існувало). Повторний прогін ПІЗНІШЕ, коли хтось уже міг вручну переставити авторів через
`PATCH /works/:id` (Stage 8e-2+), мовчки перепише той ручний порядок алфавітним — і саме тому
recovery нижче — окремий, вужчий запит, не той самий.

`RECOVERY_SQL` — точний текст, який виконує оператор, однією транзакцією:

1. `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` — блокує кожного іншого писача (і читача) цих двох
   таблиць, і сам блокується, доки не завершиться (commit або rollback) будь-яка транзакція, що вже
   тримає конфліктний лок — «зупинити писачів і дочекатися завершення їхніх транзакцій» як одна SQL-дія,
   а не окремий ручний крок, який оператор мусить не забути зробити правильно ДО recovery.
2. Creator recovery — можна перезапускати як завгодно часто: `WHERE t."createdById" IS NULL` ніколи
   не перезаписує вже заповнене значення. Той самий текст, що й `BACKFILL:CREATOR:*` у
   `20260910231627_catalog_correction_audit_schema/migration.sql`.
3. Position recovery — чіпає ЛИШЕ рядки з `position IS NULL`, дописуючи їх після наявного максимуму
   того самого `workId` (той самий порядок role → name (`COLLATE "uk-x-icu"`) → authorId, що й
   оригінальний backfill, — але лише СЕРЕД пропущених рядків, не серед усіх).
4. Відновлення `NOT NULL` — у ТІЙ САМІЙ транзакції, під тим самим локом: жоден писач не може
   вставити свіжий NULL-рядок між «заповнено» і «знову required». `COMMIT` — єдина точка, після якої
   трафік може відновитися.

```sql
BEGIN;

LOCK TABLE "Translation", "WorkAuthor" IN ACCESS EXCLUSIVE MODE;

UPDATE "Translation" t
SET "createdById" = w."createdById"
FROM "Work" w
WHERE w."id" = t."workId" AND t."createdById" IS NULL;

WITH existing_max AS (
  SELECT "workId", MAX("position") AS max_position
  FROM "WorkAuthor"
  WHERE "position" IS NOT NULL
  GROUP BY "workId"
),
missing AS (
  SELECT
    wa."workId",
    wa."authorId",
    wa."role",
    ROW_NUMBER() OVER (
      PARTITION BY wa."workId"
      ORDER BY
        CASE wa."role"
          WHEN 'AUTHOR' THEN 0
          WHEN 'CO_AUTHOR' THEN 1
          WHEN 'EDITOR' THEN 2
          WHEN 'ILLUSTRATOR' THEN 3
        END,
        a."name" COLLATE "uk-x-icu",
        wa."authorId"
    ) AS rank
  FROM "WorkAuthor" wa
  JOIN "Author" a ON a."id" = wa."authorId"
  WHERE wa."position" IS NULL
)
UPDATE "WorkAuthor" wa
SET "position" = COALESCE(existing_max.max_position + 1, 0) + (missing.rank - 1)
FROM missing
LEFT JOIN existing_max ON existing_max."workId" = missing."workId"
WHERE wa."workId" = missing."workId"
  AND wa."authorId" = missing."authorId"
  AND wa."role" = missing."role";

ALTER TABLE "Translation" ALTER COLUMN "createdById" SET NOT NULL;
ALTER TABLE "WorkAuthor" ALTER COLUMN "position" SET NOT NULL;

COMMIT;
```

Це пишеться як окрема нова forward-міграція (той самий golden rule — реальні застосовані файли не
редагуються); або як одноразовий адміністративний скрипт, якщо required-міграцію-файл достатньо
позначити застосованою пізніше. `catalog-correction-recovery.db-spec.ts` доводить на реальних
міграціях, з реальною паралельною сесією-писачем: `LOCK TABLE` справді чекає, доки та сесія
закомітить, а не просто «зазвичай встигає»; нова спроба писати, розпочата, поки `LOCK` ще чекає, теж
блокується; рядки з наявним (у тому числі неалфавітним, ручним) `position` не рухаються; NULL-рядок
дописується останнім гапless; `CatalogRevision` і `Work.revision` не чіпаються; і — крок 6 вище —
`PrismaClient`, згенерований із чинної `schema.prisma`, читає всі ці рядки без винятку одразу після
commit.

## §C. Повне видалення нової схеми (revision/createdById/position/CatalogRevision)

**Коли:** підетап остаточно згорнули ДО того, як з'явилися будь-які реальні audit-дані, і потрібно
повернути схему точно в стан до Stage 8e-1.

**Це руйнівна операція для `CatalogRevision` і для лічильників `revision`/`position`, і саме тому
вона описана окремо від §A/§B, а не як «ще один крок rollback».** Видалення `CatalogRevision` стирає
історію правок каталогу назавжди — «безпечний rollback» не є приводом це зробити мовчки. Так само, як
і §A/§B, це вимагає зупинки писачів каталогу ПЕРЕД будь-якою з дій нижче — часткове застосування
`DROP COLUMN` під живим трафіком псує дані активніше, ніж будь-який з попередніх сценаріїв.

Обов'язковий порядок, якщо цей сценарій справді потрібен:

1. **Спочатку перевірити або заархівувати**, не видаляти:
   ```sql
   SELECT count(*) FROM "CatalogRevision";
   ```
   Якщо результат не `0` — зробити дамп перед будь-якою наступною дією (`pg_dump --table='"CatalogRevision"'`
   у окремий файл, збережений поза базою) і отримати явне підтвердження від власника продукту, що
   втрата цих рядків прийнятна. Мовчазне `DROP TABLE` без цього кроку заборонене цим runbook.
2. Лише після архівації/підтвердження — нова forward-міграція, що прибирає нову схему:
   ```sql
   DROP TABLE "CatalogRevision";
   ALTER TABLE "WorkAuthor" DROP COLUMN "position";
   ALTER TABLE "Translation" DROP COLUMN "createdById";
   ALTER TABLE "Translation" DROP COLUMN "createdAt";
   ALTER TABLE "Work" DROP COLUMN "revision";
   ALTER TABLE "Translation" DROP COLUMN "revision";
   ALTER TABLE "Edition" DROP COLUMN "revision";
   DROP TYPE "CatalogEntityType";
   ```
3. Відповідний відкат `schema.prisma` (прибрати ці поля й модель `CatalogRevision`) — окремий, добре
   видимий у diff комміт, не змішаний із чимось іншим.

**Чому цей сценарій не покритий автоматизованим тестом, на відміну від §A/§B/recovery:** тест, що на
кожному прогоні `./gate.sh` видаляє audit-таблицю (навіть на scratch-БД), нормалізував би саме ту дію,
від якої цей документ застерігає, — «видалення audit-даних» стало б рутинною, непоміченою частиною
зеленого gate. §A, §B і recovery натомість доводять протилежне: що НЕ втрачати дані — можливо і
перевірено.
