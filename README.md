# BookSwap

Сервіс обміну **фізичними** книжками: користувач веде каталог книжок, що є в нього вдома, бачить бібліотеки друзів і може позичити в них книгу через запит із підтвердженням власника.

Джерело вимог — [`docs/specification.md`](docs/specification.md). За розбіжності між кодом і документом правий документ.

## Поточний стан

Каркас монорепо **плюс повна модель даних** зі §4 специфікації. Авторизація й бізнес-логіка ще не реалізовані — див. [Що далі](#що-далі).

Що працює зараз:

- монорепо на pnpm workspaces + Turborepo з наскрізними `lint` / `typecheck` / `test` / `build`;
- `apps/api` — NestJS із префіксом `/api/v1`, валідацією оточення на старті, глобальною валідацією DTO і єдиним форматом помилок;
- `apps/web` — Next.js App Router, який споживає API через спільні контракти;
- `packages/shared` — zod-схеми контрактів, спільні для бекенду й фронтенду;
- **PostgreSQL 17 + Prisma 7**: уся схема §4 (включно з `Loan` і сповіщеннями), перша міграція з `pg_trgm`/`unaccent` і GIN-індексами, `PrismaService`/`PrismaModule`, повторюваний seed і тести обмежень БД.

Схема заведена **вся одразу** — так вимагає §14: код під позичання й сповіщення пишеться на етапах 2–3, але міняти структуру таблиць посеред роботи дорожче, ніж завести їх наперед.

## Передумови

|         | Версія           | Чому саме так                                              |
| ------- | ---------------- | ---------------------------------------------------------- |
| Node.js | **22 LTS**       | §2 специфікації. Версія зафіксована в `.nvmrc` і `engines` |
| pnpm    | **11.21.0**      | §12.3: точна версія в `packageManager`, без діапазону      |
| Docker  | будь-який свіжий | лише для PostgreSQL                                        |

pnpm сам підтягне потрібну собі версію з поля `packageManager` — окремо встановлювати 11.21.0 не треба.

Якщо локальний Node не 22, pnpm виведе `[WARN] Unsupported engine`. Це попередження, не помилка: воно навмисно не глушиться, щоб розбіжність із цільовим рантаймом лишалася видимою. CI виконує всі перевірки саме на Node 22.

## Швидкий старт

```bash
cp .env.example .env      # .env — ОДИН, у корені (§12.2)
pnpm install
pnpm db:up                # PostgreSQL 17 у Docker
pnpm db:deploy            # застосувати міграції
pnpm db:seed              # демо-дані
pnpm dev                  # API :3001 + web :3000
```

Перевірити, що API живий:

```bash
curl http://localhost:3001/api/v1/health
```

API **не стартує без бази**: `DATABASE_URL` і `DIRECT_DATABASE_URL` перевіряються на старті, а `PrismaService` підключається під час ініціалізації модулів.

## Команди

Усі команди запускаються з кореня і розкладаються Turborepo по пакетах.

| Команда                             | Що робить                                                 |
| ----------------------------------- | --------------------------------------------------------- |
| `pnpm dev`                          | API у watch-режимі + Next.js dev-сервер                   |
| `pnpm build`                        | збірка `shared` → `api` → `web`                           |
| `pnpm lint`                         | ESLint, нуль попереджень (`--max-warnings=0`)             |
| `pnpm typecheck`                    | `tsc --noEmit` по всіх пакетах                            |
| `pnpm test`                         | Jest: unit у `shared` та `api`. Бази не потребує          |
| `pnpm test:db`                      | e2e + тести обмежень БД. **Потрібна запущена PostgreSQL** |
| `pnpm format` / `pnpm format:check` | Prettier                                                  |

Команди бази — в окремому розділі [нижче](#база-даних).

`build`, `typecheck`, `lint`, `test` і `dev` залежать від `^build` і від таски `generate`, тож `packages/shared` збирається, а Prisma Client генерується автоматично. З чистого клону нічого попередньо збирати вручну не треба.

## Структура

```
apps/
  api/       NestJS — REST під /api/v1
    prisma/  schema.prisma, міграції, seed
    src/
      prisma/     PrismaModule + PrismaService
      generated/  Prisma Client (генерується, у git не тримається)
  web/       Next.js App Router
packages/
  shared/    zod-схеми контрактів + коди помилок (§12.1)
docs/
  specification.md
```

`packages/shared` існує з першого дня навмисно (§12.1): щойно фронт почне імпортувати типи з `apps/api`, монорепо перетвориться на два застосунки з кільцевою залежністю.

## Домовленості

### Помилки API

Кожна помилка має машиночитний `code` (§8):

```json
{ "code": "NOT_FOUND", "message": "Cannot GET /api/v1/nope" }
```

HTTP-статус зберігається як є; `code` — додатковий машиночитний шар поверх нього. Відповіді `5xx` ніколи не розкривають оригінальне повідомлення чи stack — вони йдуть у лог, а назовні віддається стале `Internal server error`.

Коди живуть у `packages/shared` (`API_ERROR_CODES`). Зараз їх лише вісім — загальних, інфраструктурних. Доменні коди додаються **разом** зі своєю функціональністю, а не наперед.

Доменний виняток задає власний код через `ApiException`, і глобальний фільтр віддає його без змін:

```ts
throw new ApiException(API_ERROR_CODES.CONFLICT, 'Копія вже позичена', HttpStatus.CONFLICT)
```

### Валідація

Два механізми, і вони не замінюють один одного (§11):

- **DTO ендпоінтів** валідуються в рантаймі через `class-validator` глобальним `ValidationPipe`;
- **схеми контрактів** живуть у `packages/shared` як zod і спільні для бекенду та фронтенду.

Коли зʼявиться перший доменний DTO, тримай його форму звіреною зі схемою з `shared` — наприклад, типовою перевіркою присвоюваності класу до `z.infer<typeof schema>`. Розсинхрон між двома описами однієї структури — головний ризик цієї пари.

### Оточення

`.env` — **один, у корені** (§12.2). `apps/api` читає його явним шляхом; `apps/web` бере з нього **лише** змінні з префіксом `NEXT_PUBLIC_`, тож серверні секрети не потрапляють ані в клієнтський бандл, ані навіть у процес складання Next.

Prisma 7 більше не підвантажує `.env` сама, тож `apps/api/prisma.config.ts` робить це явно — тим самим шляхом, що й `AppModule`.

`DATABASE_URL` і `DIRECT_DATABASE_URL` **обов'язкові**: без них не стартує API і не працює `prisma generate`.

## База даних

PostgreSQL 17 у Docker, Prisma 7 як ORM. Схема — `apps/api/prisma/schema.prisma`, джерело правди — §4 специфікації.

### Команди

| Команда                       | Що робить                                                              |
| ----------------------------- | ---------------------------------------------------------------------- |
| `pnpm db:up` / `pnpm db:down` | підняти / зупинити PostgreSQL у Docker                                 |
| `pnpm db:generate`            | згенерувати Prisma Client                                              |
| `pnpm db:migrate`             | створити й застосувати міграцію за змінами схеми (dev)                 |
| `pnpm db:migrate:create`      | створити міграцію **без** застосування — для ручних правок SQL         |
| `pnpm db:deploy`              | застосувати наявні міграції (CI, прод, чиста локальна база)            |
| `pnpm db:seed`                | наповнити базу демо-даними; повторний запуск нічого не дублює          |
| `pnpm db:reset`               | дропнути базу, накатати міграції заново, виконати seed. **Незворотно** |
| `pnpm test:db`                | e2e + тести обмежень БД на окремій тестовій базі                       |

`db:generate` рідко потрібен окремо: від нього залежать `build`, `typecheck`, `lint` і `test` через turbo-таску `generate`.

### Тестова база

`pnpm test:db` працює не з dev-базою, а з окремою (`TEST_DATABASE_URL`), яку **дропає й створює заново на кожному прогоні**, після чого накатує міграції. Тобто кожен запуск заразом перевіряє, що чиста PostgreSQL приймає всю історію міграцій з нуля. Достатньо, щоб контейнер був піднятий — саму базу створить `test/db/global-setup.ts`.

> ⚠️ **`test:db` виконує `DROP DATABASE`.** Перед цим `test/db/guard.ts` робить **fail-closed** перевірку, і без неї жодного підключення не відбувається. Дропнути можна лише базу, яка:
>
> - має назву за шаблоном `^[A-Za-z0-9_]+_test$` — whitelist, тож лапки, пробіли, слеші й будь-які SQL-фрагменти не проходять за побудовою;
> - не є `postgres`, `template0` чи `template1`;
> - лежить на `localhost`, `127.0.0.1` або `::1` — віддалений хост заборонено завжди;
> - не збігається з `DATABASE_URL` або `DIRECT_DATABASE_URL` за нормалізованими host / port / назвою (петльові адреси зводяться до однієї, порт за замовчуванням добирається — щоб та сама база, записана іншим рядком, не проскочила).
>
> Будь-яке порушення — виняток, а не фолбек. Перевірка чиста й покрита unit-тестами в `test/db/guard.spec.ts`, які їдуть у `pnpm test` без PostgreSQL.

Jest тут запускається через `node --experimental-vm-modules`: Rust-free клієнт Prisma 7 підвантажує WASM-компілятор запитів динамічним `import()`, а той у пісочниці Jest без цього прапорця недоступний.

### Правка міграцій руками

Дещо з §4.9 і §5.3 Prisma Schema Language не виражає, тож ці рядки дописані в `migration.sql` вручну:

```sql
-- на самий початок першої міграції
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;

-- у кінець
CREATE UNIQUE INDEX one_active_loan_per_copy
  ON "Loan" ("copyId")
  WHERE status IN ('APPROVED', 'HANDED_OVER');
```

Порядок критичний: GIN-індекси нижче в тому ж файлі використовують `gin_trgm_ops`, і на **чистій** базі вони впадуть, якщо розширення ще немає. Локально цього не видно — розширення в старій базі вже є, помилка проявиться при першому розгортанні на сервері. Саме тому job `database` у CI щоразу піднімає порожній контейнер.

Самі GIN-індекси у Prisma Schema **є** (`type: Gin, ops: raw("gin_trgm_ops")`), тож генеруються автоматично й не розходяться зі схемою. Поза її знанням лишається тільки `one_active_loan_per_copy`. Перевірено `prisma migrate diff`: Prisma його не бачить і дропнути не пропонує. Якщо колись увімкнути preview-фічу `partialIndexes`, це зміниться — тоді індекс треба буде або перенести в схему, або вичитувати кожну нову міграцію.

Робочий цикл для будь-якої зміни, яку Prisma не вміє висловити:

```bash
pnpm db:migrate:create --name <назва>   # згенерувати, але не застосовувати
# → дописати SQL руками в prisma/migrations/<ts>_<назва>/migration.sql
pnpm db:deploy                          # застосувати
```

### Чим Prisma 7 відрізняється від блоку в §4.1

§4.1 писався під Prisma 6 і прямо просить звірити його з фактичною версією. Розбіжності:

| §4.1                               | Prisma 7.9                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| `provider = "prisma-client-js"`    | deprecated → `prisma-client`, і `output` тепер обов'язковий                      |
| `binaryTargets` із `linux-arm64`   | поля немає: Rust-движок прибрано, нативних бінарників більше не існує            |
| `url` / `directUrl` у `datasource` | перенесені в `prisma.config.ts`; `directUrl` як поле видалено                    |
| `extensions = [pg_trgm, unaccent]` | preview `postgresqlExtensions` згорнуто → `CREATE EXTENSION` сирим SQL (як §4.9) |
| `.env` підвантажується сам         | більше ні — `prisma.config.ts` вантажить кореневий `.env` явно                   |
| вбудовані драйвери                 | обов'язковий драйвер-адаптер `@prisma/adapter-pg` поверх `pg`                    |

**ARM (§13.1) від цього не постраждав, а спростився.** Вимога `binaryTargets` існувала тільки тому, що query engine був нативним бінарником під конкретну платформу. У сімці його немає — клієнт це TypeScript плюс WASM, однаковий на x86 і ARM. Пропуск `binaryTargets`, який у шістці проявився б помилкою про відсутній engine вже на сервері, тут неможливий.

**Намір `directUrl` збережено, механізм інший.** Міграції беруть advisory lock, який не переживає transaction pooling PgBouncer'а, тож ходити вони мусять напряму. Розподіл такий:

- `DIRECT_DATABASE_URL` → `prisma.config.ts` → Prisma CLI: міграції, introspection, seed;
- `DATABASE_URL` → драйвер-адаптер у `PrismaService` → рантайм застосунку.

Локально це той самий рядок, у проді — різні.

## Що далі

Етапи зі §14 специфікації:

1. **Кістяк** — auth (session cookie), профіль, дружба, `Work`/`Translation`/`Edition`/`Copy`, особиста бібліотека. Схема Prisma заведена вся одразу — ✅ зроблено; лишається API поверх неї.
2. **Позичання** — стейт-машина §5 з транзакціями й тестом на конкурентний апрув, історія, in-app сповіщення.
3. **Сповіщення назовні** — email, диспетчер із ретраями, Telegram-бот.
4. **Якість даних** — fuzzy-пошук, автозаповнення за ISBN, мердж дублікатів, вішлист.
5. **Оцінки** — `Review`, `TranslationRating`, ранг перекладів із cold-start-правилом.

Ключове з домену, що не можна спрощувати: `Work → Translation → Edition → Copy` — чотири різні сутності, і **позичається завжди `Copy`**. Кількість примірників — це `COUNT` рядків `Copy`, а не поле `quantity`.
