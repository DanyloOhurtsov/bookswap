# BookSwap

Сервіс обміну **фізичними** книжками: користувач веде каталог книжок, що є в нього вдома, бачить бібліотеки друзів і може позичити в них книгу через запит із підтвердженням власника.

Джерело вимог — [`docs/specification.md`](docs/specification.md). За розбіжності між кодом і документом правий документ.

## Поточний стан

Повна модель даних зі §4 **плюс акаунт, сесії, профіль, дружба, каталог, особиста бібліотека, позичання зі стейт-машиною §5, історія §6.6 та in-app сповіщення**. Далі — доставка сповіщень назовні, див. [Що далі](#що-далі).

Що працює зараз:

- монорепо на pnpm workspaces + Turborepo з наскрізними `lint` / `typecheck` / `test` / `build`;
- **PostgreSQL 17 + Prisma 7**: уся схема §4 (включно з `Loan` і сповіщеннями), міграції з `pg_trgm`/`unaccent` і GIN-індексами, `PrismaService`/`PrismaModule`, повторюваний seed і тести обмежень БД;
- **акаунт і автентифікація** (§6.1): реєстрація, вхід, вихід, серверні session cookies, підтвердження пошти й скидання пароля одноразовими токенами, rate limiting на чутливих ендпоінтах;
- **профіль**: перегляд і редагування пʼяти полів §6.1, пошук людей за імʼям і за точною адресою;
- **дружба** (§6.2): запит, згода, відмова, видалення, блокування — усі переходи крізь одну стейт-машину, зі сповіщеннями `FRIEND_REQUESTED` / `FRIEND_ACCEPTED` у тій самій транзакції;
- **централізована авторизація видимості** (§9): `AccessService` плюс чисті функції правил — єдине місце, де живе відповідь на питання «чи можна це бачити»;
- **каталог** (§6.3): fuzzy-пошук по `Work` і `Author` через `pg_trgm` + `unaccent`, ручне створення ланцюга `Work → Translation → Edition`, ISBN-13 із контрольною сумою, коди мов ISO 639-1;
- **особиста бібліотека** (§6.4) і **бібліотека іншої людини** (§6.5): примірники з групуванням за виданням, фільтри, в'ю «мої не вдома» / «чужі в мене», видимість за матрицею §9;
- **позичання** (§5): уся таблиця переходів §5.1 крізь один `LoanService`, конкурентний апрув через `SELECT … FOR UPDATE` на `Copy` плюс частковий унікальний індекс, інваріанти §5.3 і в коді, і CHECK'ами в БД;
- **історія** (§6.6): примірника, твору («хто з моїх це читав») і власна — виводиться з `Loan`, з окремою анонімною проєкцією для §9;
- **in-app сповіщення** (§7): читання, позначення прочитаним, лічильник непрочитаних; запис — у тій самій транзакції, що й перехід;
- `apps/web` — сторінки реєстрації, входу, підтвердження пошти, скидання пароля, захищений профіль, `/friends`, `/catalog`, `/works/[id]`, майстер додавання книжки, `/library`, бібліотека друга з кнопкою «Попросити», `/loans`, `/history`, `/copies/[id]/history` і `/notifications`;
- `packages/shared` — zod-контракти всіх цих запитів і відповідей, спільні для бекенду й фронтенду.

Схема БД заведена **вся одразу** — так вимагає §14: код під зовнішні канали сповіщень пишеться на наступному етапі, але міняти структуру таблиць посеред роботи дорожче, ніж завести їх наперед.

## Передумови

|         | Версія           | Чому саме так                                              |
| ------- | ---------------- | ---------------------------------------------------------- |
| Node.js | **22 LTS**       | §2 специфікації. Версія зафіксована в `.nvmrc` і `engines` |
| pnpm    | **11.21.0**      | §12.3: точна версія в `packageManager`, без діапазону      |
| Docker  | будь-який свіжий | лише для PostgreSQL                                        |

pnpm сам підтягне потрібну собі версію з поля `packageManager` — окремо встановлювати 11.21.0 не треба.

Якщо локальний Node не 22, pnpm виведе `[WARN] Unsupported engine`. Це попередження, не помилка: воно навмисно не глушиться, щоб розбіжність із цільовим рантаймом лишалася видимою. CI виконує всі перевірки саме на Node 22.

## Швидкий старт

```bash
cp .env.example .env      # .env — ОДИН, у корені (§12.2)
pnpm install
pnpm db:up                # PostgreSQL 17 у Docker
pnpm db:deploy            # застосувати міграції
pnpm db:seed              # демо-дані
pnpm dev                  # API :3001 + web :3000
```

Перевірити, що API живий:

```bash
curl http://localhost:3001/api/v1/health
```

Далі — <http://localhost:3000/register>. Пошта локально нікуди не йде: лист із посиланням на підтвердження друкується **в лог API** (див. [Пошта](#пошта)).

API **не стартує без бази**: `DATABASE_URL` і `DIRECT_DATABASE_URL` перевіряються на старті, а `PrismaService` підключається під час ініціалізації модулів.

## Домовленості

### Помилки API

Кожна помилка має машиночитний `code` (§8):

```json
{ "code": "NOT_FOUND", "message": "Cannot GET /api/v1/nope" }
```

HTTP-статус зберігається як є; `code` — додатковий машиночитний шар поверх нього. Відповіді `5xx` ніколи не розкривають оригінальне повідомлення чи stack — вони йдуть у лог, а назовні віддається стале `Internal server error`.

Коди живуть у `packages/shared` (`API_ERROR_CODES`). Вісім загальних, інфраструктурних, плюс доменні, що приїжджають разом зі своєю функціональністю, а не наперед:

- акаунти: `EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `INVALID_TOKEN`;
- дружба: `FRIENDSHIP_SELF`, `FRIENDSHIP_EXISTS`, `FRIENDSHIP_BLOCKED`, `FRIENDSHIP_INVALID_TRANSITION`;
- каталог і бібліотека: `EDITION_ISBN_TAKEN`, `COPY_HAS_ACTIVE_LOAN`, `COPY_STATUS_LOCKED`;
- позичання: `LOAN_SELF`, `LOAN_COPY_UNAVAILABLE`, `LOAN_DUPLICATE_REQUEST`, `LOAN_INVALID_TRANSITION`, `LOAN_COPY_STATE_MISMATCH`, `LOAN_ALREADY_APPROVED`.

Коди заводяться лише там, де клієнт справді має розрізняти випадки. Порушення ролі (прийняти власний запит, зняти чужий блок) лишається загальним `FORBIDDEN`, відсутній рядок — `NOT_FOUND`: окремий код нічого не додав би до дії, яку фронт усе одно виконує однаково.

`EDITION_ISBN_TAKEN` — єдиний код, що несе ще й `details`: там лежить `{ editionId }` наявного видання. Це не діагностика, а маршрут: §6.3 хоче, щоб людину довели до вже заведеного запису, де їй лишається створити тільки `Copy`. Раніше `ApiException` приймав `details`, але глобальний фільтр їх не віддавав — тепер віддає, і це закріплено тестом.

Доменний виняток задає власний код через `ApiException`, і глобальний фільтр віддає його без змін:

```ts
throw new ApiException(API_ERROR_CODES.CONFLICT, 'Копія вже позичена', HttpStatus.CONFLICT)
```

### Валідація

Два механізми, і вони не замінюють один одного (§11):

- **DTO ендпоінтів** валідуються в рантаймі через `class-validator` глобальним `ValidationPipe`;
- **схеми контрактів** живуть у `packages/shared` як zod і спільні для бекенду та фронтенду.

Розсинхрон між двома описами однієї структури — головний ризик цієї пари, тож він перевіряється тестом, а не домовленістю: `apps/api/src/auth/dto/auth.dto.spec.ts` жене однакові дані крізь обидва механізми й вимагає однакового вироку на кожному межовому значенні. Числові обмеження при цьому не дублюються — DTO беруть їх із `PROFILE_LIMITS` і `PASSWORD_LIMITS` у `shared`.

Правила про **пару полів** (`оновити хоч щось`, `рівно один параметр пошуку`) class-validator не виражає — вони живуть у zod для фронту й перевіряються контролером на бекенді. Ця розбіжність теж зафіксована тестом, щоб лишалася явною.

### Оточення

`.env` — **один, у корені** (§12.2). `apps/api` читає його явним шляхом; `apps/web` бере з нього **лише** змінні з префіксом `NEXT_PUBLIC_`, тож серверні секрети не потрапляють ані в клієнтський бандл, ані навіть у процес складання Next.

Prisma 7 більше не підвантажує `.env` сама, тож `apps/api/prisma.config.ts` робить це явно — тим самим шляхом, що й `AppModule`.

`DATABASE_URL` і `DIRECT_DATABASE_URL` **обов'язкові**: без них не стартує API і не працює `prisma generate`.

Терміни життя сесій і токенів у оточення **не винесені** — вони однакові в усіх середовищах і лежать константами в `apps/api/src/auth/auth.constants.ts`. Єдине, що залежить від середовища, — атрибут `Secure` на кукі, і він виводиться з `NODE_ENV`.

### Як влаштована автентифікація

**Session cookie, не JWT** (§6.1). Кукі `bookswap_session` несе випадковий 256-бітний токен; у базі лежить лише його SHA-256. Дамп таблиці `Session` тому не дає можливості видати себе за когось.

Атрибути кукі: `HttpOnly` (XSS не виносить сесію), `SameSite=Lax` (базовий захист від CSRF), `Path=/`, `Secure` — **тільки в production**, бо локально все по `http://localhost`. `SameSite=Lax` достатньо саме тому, що в проді фронт і бек за одним доменом через Caddy (§13.2); у dev `localhost:3000` → `localhost:3001` теж same-site, порт на це не впливає.

**Паролі** — scrypt із `node:crypto`, memory-hard KDF без нативних збірок. bcrypt і argon2 тягнуть за собою компіляцію, а прод за §13.1 це ARM, де кожен нативний модуль — окремий ризик на деплої. Параметри зберігаються поруч із гешем (`scrypt$N$r$p$salt$hash`), тож їх можна підняти, не ламаючи наявні паролі.

**Що навмисно не розкривається.** Логін відповідає однаково на невідому адресу й на невірний пароль — і кодом, і текстом, і часом (для невідомої адреси все одно рахується геш). Запит на скидання пароля завжди повертає `202 { accepted: true }`, незалежно від того, чи існує акаунт.

**Одноразовість токенів** тримається умовою `usedAt IS NULL` в самому `UPDATE`, а не перевіркою перед ним: дві паралельні спроби дають рівно одне погашення. Успішне скидання пароля відкликає **всі** сесії користувача й гасить решту невикористаних reset-токенів.

**Прострочене** прибирається `SessionCleanupService` раз на чверть години. Це гігієна таблиць, а не безпека: прострочена сесія не працює й до прибирання — `expiresAt` звіряється на кожному запиті.

**Rate limiting** (§11) висить точково на чутливих маршрутах, а не глобально: реєстрація — 5/год, логін — 10/15 хв, листи — 5/год, погашення токенів — 20/год, пошук — 60/хв. Лічильник у пам'яті процесу; Redis §2 виключає зі стека v1.

**`trust proxy = 1` — тільки в production.** За Caddy (§13.2) Express без цього бачить IP проксі, однаковий для всіх, і ліміт спроб входу стає глобальним: перший, хто його вичерпає, замикає вхід усім. Локально ж проксі немає, і `X-Forwarded-For` цілком контролюється клієнтом — довіряти йому в dev означало б роздати спосіб обійти будь-який ліміт зміною заголовка. Значення саме `1`, а не `true`: довіряється рівно один стрибок, найближчий проксі. Обидві поведінки перевіряє `proxy-rate-limit.e2e-spec.ts`.

**Підтвердження пошти запускає людина кнопкою**, а не сторінка при відкритті. Токен одноразовий, а за посиланням із листа ходять не лише люди: поштові сканери безпеки, антивіруси й префетчери переходять за ним самі й погасили б токен ще до того, як користувач побачить сторінку.

### Пошта

Локально листи **нікуди не надсилаються** — `DevEmailSender` друкує їх у лог API цілком, разом із посиланням:

```
[Nest] LOG [DevEmailSender] Лист (dev, нікуди не відправлено) → marta@example.com
Тема: BookSwap: підтвердіть адресу
…
http://localhost:3000/verify-email?token=IcFmlW77np_bCtqdrZC9LDVwFCKtGXg0a3Kwbo8rnMs
```

Це єдиний спосіб пройти підтвердження пошти на свіжому клоні, тому тіло друкується на рівні `log`, а не `debug`. Реальний провайдер (Resend або Postmark, §2) стане ще однією реалізацією порту `EmailSender` на етапі сповіщень — без правок у сервісі акаунтів.

> ⚠️ **З `NODE_ENV=production` застосунок із цим відправником не стартує взагалі** — `DevEmailSender` кидає на етапі створення. Причини дві, і обидві серйозні: він нічого не надсилає (підтвердження пошти й скидання пароля мовчки не працюють, і дізнаєшся про це з тікетів) і пише тіло листа з одноразовим токеном у лог та в пам'ять. Краще впертися в помилку деплою, ніж у мовчазно зламаний прод. Знімається це не прапорцем, а підключенням справжнього провайдера.

## Дружба та видимість

### Ендпоінти

```
GET    /api/v1/friends                     список друзів
GET    /api/v1/friends/requests            вхідні + вихідні одним відгуком
POST   /api/v1/friends/requests            { userId }
PATCH  /api/v1/friends/requests/:id        { action: accept | decline }
DELETE /api/v1/friends/:userId             розірвати звʼязок; ним же знімається блок
POST   /api/v1/friends/:userId/block
```

`GET /users` тепер віддає не голий список людей, а `{ results: [{ user, relation }] }`. `relation` — стан пари **з погляду того, хто питає**: `NONE`, `REQUEST_SENT`, `REQUEST_RECEIVED`, `FRIENDS`, `BLOCKED_BY_ME`, `BLOCKED_ME`. Рахує його API, а не фронт: клієнт, який виводив би «чи ми друзі» перетином двох списків, продублював би авторизаційну логіку за мережею — і все одно не дізнався б про блокування, бо заблокованих пар немає в жодному зі списків.

Назовні `FriendshipStatus` не віддається взагалі. `PENDING` сам по собі не каже, яку кнопку малювати — «Прийняти» чи «Скасувати запит»; щоб відповісти, потрібен ще `requestedById`.

### Стейт-машина

Усі переходи — крізь один метод `FriendsService.apply()`, як §5 вимагає для лоанів. Рішення «можна чи ні» ухвалює **чиста** `resolveTransition()` у `friends/friendship.transitions.ts`: вона не має доступу до бази, тож обійти її з контролера технічно неможливо. Стан `NONE` означає «рядка немає» і є повноцінним станом.

| Звідки                    | Дія            | Хто                    | Куди                       | Ефекти (одна транзакція)                               |
| ------------------------- | -------------- | ---------------------- | -------------------------- | ------------------------------------------------------ |
| `NONE`                    | request        | будь-хто, крім себе    | `PENDING`                  | `Notification(FRIEND_REQUESTED)` отримувачу            |
| `DECLINED`                | request        | будь-хто з пари        | `PENDING`                  | те саме; ініціатор перезаписується                     |
| `PENDING`                 | request        | **отримувач**          | `ACCEPTED`                 | зустрічний запит = згода; `FRIEND_ACCEPTED` ініціатору |
| `PENDING`                 | request        | ініціатор              | ✗ 409 `FRIENDSHIP_EXISTS`  | —                                                      |
| `PENDING`                 | accept         | **отримувач**          | `ACCEPTED`                 | `FRIEND_ACCEPTED` ініціатору                           |
| `PENDING`                 | accept/decline | ініціатор              | ✗ 403 `FORBIDDEN`          | не можна відповісти на власний запит                   |
| `PENDING`                 | decline        | отримувач              | `DECLINED`                 | сповіщення немає                                       |
| `PENDING`                 | remove         | будь-хто з пари        | видалення                  | скасувати свій запит або прибрати чужий                |
| `ACCEPTED`                | remove         | будь-хто з пари        | видалення                  | **активні `Loan` не чіпаються** (§5.2)                 |
| будь-який, крім `BLOCKED` | block          | будь-хто з пари        | `BLOCKED`                  | `blockedById` = актор                                  |
| `BLOCKED`                 | remove         | **лише `blockedById`** | видалення                  | розблокування                                          |
| `BLOCKED`                 | будь-що інше   | будь-хто               | ✗ 403 `FRIENDSHIP_BLOCKED` | —                                                      |

Чотири рішення, які варто назвати вголос:

- **`DECLINED` не вирок.** Повторний запит після відмови дозволений: інакше одне випадкове «Відхилити» закриває пару назавжди, а §6.2 не дає способу це скасувати. Від настирливості захищає rate limiting (§11, 30 запитів на годину) і блокування.
- **Зустрічний запит авто-приймається.** Обидві сторони висловили той самий намір; змушувати другого шукати вхідний запит — тертя без сенсу. Наслідок для фронту: `POST /friends/requests` може повернути `FRIENDS`, і читати треба `relation` з відповіді, а не припускати `REQUEST_SENT`.
- **Відкликати власний запит — це `remove`, а не `decline`.** Після скасування власного запиту сліду `DECLINED` лишатися не повинно.
- **Сповіщень рівно два.** §7.5 перелічує `FRIEND_REQUESTED` і `FRIEND_ACCEPTED` — і все. «Вас відхилили» нікому не допомагає, «вас заблокували» ще й підказує завести другий акаунт.

### Конкурентність

Сирий `SELECT … FOR UPDATE` тут не потрібен — §5.2 вимагає його для `Copy`, де конфліктують стан рядка й стан лоану; у дружби конфлікт лише за один рядок.

- **Два одночасні `INSERT`** (обидва натиснули «додати» разом) ловить `@@unique([userAId, userBId])`. Той, хто програв, отримує `P2002`, і вся транзакція повторюється — на другому проході рядок суперника вже видно, тож сценарій сходиться до `ACCEPTED`, а не до 409. Повтор ловиться **зовні** транзакції навмисно: порушення обмеження перериває транзакцію Postgres цілком, і продовження в ній упало б з `25P02`.
- **Одночасні зміни наявного рядка** (accept із двох вкладок) тримає умова на `status` у самому `UPDATE` плюс перевірка `count === 1` — той самий оптимістичний прийом, яким `AuthService` тримає одноразовість токенів із листів.
- **Застарілий id запиту.** `PATCH /friends/requests/:id` адресує конкретний рядок, тож рядок і читається за `id` — **усередині** тієї самої транзакції, що його змінює. Читати за id зовні, а змінювати за парою було б помилкою: `cuid` видаленого рядка ніколи не повертається, тож між двома читаннями запит можна скасувати й створити новий для тієї самої пари — і стара вкладка з давнім id прийняла б щойно створений чужий запит. Різницю між «адресуємо людину» і «адресуємо рядок» несе тип `FriendshipTarget`, а розвʼязує її `FriendsService.locate()`.

### `blockedById` — відхилення від §4.3

Схема §4.3 має `requestedById`, але не має поля «хто заблокував». Без нього статус `BLOCKED` симетричний: неможливо ні відрізнити «я заблокував» від «мене заблокували», ні вирішити, кому дозволено зняти блок. `requestedById` для цього не годиться — §4.3 прямо вимагає тримати ініціатора запиту окремо, і перевантажити його означало б втратити історію.

Тому в моделі зʼявилося `blockedById String?` — з повноцінним зовнішнім ключем на `User` (`ON DELETE CASCADE`). На відміну від `requestedById`, який лишається голим рядком, тут від поля залежить **право**: знімати блок може лише той, хто в ньому записаний. Право не можна тримати на значенні, якого база не перевіряє.

Решту гарантує CHECK `friendship_block_author_valid`:

```sql
CHECK (
  CASE
    WHEN "status" = 'BLOCKED'::"FriendshipStatus"
      THEN "blockedById" IS NOT NULL
           AND ("blockedById" = "userAId" OR "blockedById" = "userBId")
    ELSE "blockedById" IS NULL
  END
)
```

Три вимоги одним виразом: `BLOCKED` → автор є; автор — один з учасників пари; не-`BLOCKED` → автора немає.

**Чому `CASE`, а не кон'юнкція порівнянь.** CHECK у PostgreSQL пропускає рядок, коли вираз дає `TRUE` **або `NULL`** — і на цьому такі перевірки тихо перестають працювати. Наївне `blockedById IN ("userAId", "userBId")` для `NULL` дає `NULL`, тобто рядок без автора проходить. Тут кожна гілка повертає строго `TRUE` або `FALSE`: у гілці `BLOCKED` `NULL IS NOT NULL` → `FALSE`, а `FALSE AND NULL` → `FALSE`; гілка `ELSE` — це `IS NULL`, яке NULL не буває; сам предикат `WHEN` теж не буває NULL, бо `status` — `NOT NULL`. Перевірка fail-closed: щоб пройти, рядок мусить бути явно правильним.

Порядок спрацювання варто знати: CHECK'и PostgreSQL перевіряє під час вставки кортежу, а FK — тригером після неї. Тому неіснуючий `blockedById` відсікає саме CHECK (він завідомо не дорівнює ні `userAId`, ні `userBId`), і FK як окрема причина відмови недосяжний. Його цінність — у каскаді при видаленні користувача та в тому, що право не висить на неперевіреному рядку.

Розблокування — це `DELETE /friends/:userId` від того, хто в `blockedById`. Окремого маршруту §8 не має, і заводити його понад специфікацію підстав немає: «прибрати звʼязок» — одна дія. Дістатися до кнопки можна пошуком: заблокована пара не потрапляє ні в друзі, ні в запити, але в результатах пошуку має `relation = BLOCKED_BY_ME`.

**Відоме обмеження:** один рядок несе одного блокувальника, тож поки пара заблокована, друга сторона не може заблокувати у відповідь — вона отримає 403. Захист від цього не страждає (блокування вже симетричне в частині доступу), але якщо колись знадобиться напрямок, це буде окрема таблиця `Block`, а не друге поле тут.

### Матриця §9

Правила видимості живуть у `apps/api/src/access/` і поділені надвоє навмисно:

- **`visibility.ts` — чисті функції.** `strictestVisibility`, `isVisibleTo`, `copyVisibleTo`, `holderNamesVisibleTo`. Ні Prisma, ні Nest: рішення «чи видно» — це порівняння двох enum'ів і однієї ролі, а не запит. Тому матриця §9 покривається unit-тестом повністю й без PostgreSQL.
- **`AccessService` — те, що ходить у базу.** `findPair`, `roleOf`, `isBlocked`, `assertNotBlocked`, `relationsWith`. Це єдине місце, звідки читається `Friendship` заради авторизації.

Ключове правило §9: **видимість примірника = найсуворіше з видимості бібліотеки та самого примірника** (`PRIVATE` > `FRIENDS` > `PUBLIC`). `PUBLIC`-примірник у `PRIVATE`-бібліотеці лишається схованим — інакше одне поле на примірнику мовчки скасовувало б налаштування профілю. Імена тримачів (§6.6) власник бачить завжди, друг — за `showHolderNames`, сторонній — ніколи, навіть з увімкненим прапорцем.

**Ролей чотири, а не три.** До `OWNER` / `FRIEND` / `OTHER` додається `BLOCKED`, і це не формальність. §6.2 каже «заблокований не бачить бібліотеку» — без застережень про `Visibility`. Якби блокування зводилося до «стороннього», `PUBLIC`-бібліотека лишалася б видимою заблокованому, тобто блокування мовчки не працювало б саме для тих, хто відкрився світу. Перевірка ролі `BLOCKED` стоїть **першою** в кожній функції: блокування сильніше за будь-яку видимість, і порядок тут — це саме правило, а не оптимізація. Заблокованому недоступні бібліотека, примірники, історія й імена тримачів — за будь-якого значення `Visibility` та `showHolderNames`.

**Про споживачів.** `findPair`, `assertNotBlocked` і `relationsWith` викликають модуль дружби та пошук людей. `roleOf` разом із `isVisibleTo`, `copyVisibleTo` і `holderNamesVisibleTo` довгий час викликалися **лише з тестів** — і саме заради цього моменту трималися: перший реальний споживач — `GET /users/:id/library`. Ставка виправдалася буквально: модуль бібліотеки не написав жодного власного `findFirst` по `Friendship`, і §9 лишилася таблицею, а не набором умов, що розповзаються по контролерах.

### Сповіщення

Створюються **тільки** рядки `Notification` (`IN_APP`-подія), у тій самій транзакції, що й зміна дружби — §7.3, правило 1. `payload` — `{ actorId, friendshipId }`.

`NotificationDelivery` навмисно не створюється: рядок доставки має сенс лише разом із воркером, який його забирає (§7.3, правило 2). Без диспетчера він назавжди лишиться `PENDING`, тобто таблиця черги брехатиме про свій стан. Диспетчер, канали (email, Telegram) і ретраї — етап 3 зі §14.

Читання сповіщень описане в розділі [Сповіщення](#сповіщення).

### Ланцюг §3 лишається ланцюгом

`Work → Translation → Edition → Copy` — чотири сутності, і жодна не має полів іншої. Каталог (`catalog/`) не знає про примірники взагалі: у відповідях `/works/:id` і `/catalog/search` немає ні `Copy`, ні власників. Хто чим володіє — справа `library/`, і туди веде матриця §9. Змішати їх означало б віддавати чужі полиці з ендпоінта, у якого немає поняття «хто питає».

Кількість примірників — це `COUNT` рядків `Copy` (§3), тож у `POST /me/library` немає й не може бути поля «скільки»: два однакові томи — два запити.

### Нормалізація живе в БД, а не в TypeScript

`titleNorm` мусить збігатися з нормалізованим пошуковим запитом **символ у символ**, інакше fuzzy мовчки не знаходить нічого. Тому визначення одне — SQL-функція `bookswap_norm`, і нею користуються всі: запис `Work.titleNorm`, запис `Author.nameNorm`, нормалізація запиту в пошуку, фільтр `?q=` в бібліотеці й `prisma/seed.ts`.

TS-копії тут бути не може, і це перевірено на живій базі:

```
lower(unaccent('Café Zürich Їжак'))  →  cafe zurich їжак
```

Postgres знімає латинську діакритику, але українські літери лишає собою. Наївне зняття діакритики через NFD у JS (саме таке було в seed) перетворило б `Їжак` на `іжак` — і пошук розійшовся б на першому ж слові з `ї` чи `й`.

Ціна — один round trip на запис у каталог. Створення твору рідкісне й обмежене rate limiting'ом (§11); розсинхрон нормалізації ціни не має.

### Пошук: `%`, а не `similarity() > 0.3`

§6.3 описує поріг як `similarity(titleNorm, $1) > 0.3`, але **`similarity()` не використовує GIN-індекс** — індексований лише оператор `%`, який читає поріг із `pg_trgm.similarity_threshold`. Тому пошук іде в транзакції, яка спершу фіксує поріг через `set_config('pg_trgm.similarity_threshold', '0.3', true)`, і далі використовує `%`. Дефолт у Postgres і так 0.3, але покладатися на налаштування чужого сервера означало б мати різну поведінку пошуку локально й у проді.

До `%` додано ще `LIKE '%…%'`. Причина арифметична: триграмна схожість «шан» проти «шантарам» дорівнює рівно 0.3, тобто **не** проходить поріг, а «ґре» проти «ґреґорі девід робертс» — узагалі 0.13. Пошук замовкав би саме тоді, коли людина тільки почала друкувати. `LIKE` з обома боками теж лягає на триграмний GIN-індекс, тож ця гілка не робить запит послідовним скануванням. Символи `%` і `_` у запиті екрануються — інакше «100%» став би шаблоном «усе підряд».

`LIKE` стоїть на **обох** колонках — і `titleNorm`, і `nameNorm`, — в обох запитах. Асиметрія тут не помітна одразу й дає зіпсовану видачу: короткий фрагмент імені знаходив автора в списку `authorMatches`, але жодної його книжки в `results`. Це закріплено e2e-регресією «короткий фрагмент імені автора знаходить і його твір, і його самого».

Сирим лишається рівно ранжування: запит повертає **тільки id і оцінки**, а самі записи підтягує типізований `findMany`. Це перший і поки єдиний `$queryRaw` у продакшн-коді.

### `Author.nameNorm` — відхилення від §4.4

§4.4 дає `Author` лише сире `name` з GIN-індексом по ньому. Але `similarity()` регістрозалежна: «ґреґорі» проти «Ґреґорі Робертс» дає майже нуль спільних триграм, тобто пошук за автором через такий індекс просто не працює. Тому додано `nameNorm` — дзеркало наявного `Work.titleNorm`, заповнюване тією ж `bookswap_norm`. GIN-індекс `author_name_trgm_idx` переїхав на неї; звичайний `@@index([nameNorm])` лишається для точного пошуку.

Колонка **не унікальна**, і це продуктове рішення: тезки бувають. Автор ніколи не підбирається автоматично за збігом імені — `POST /works` приймає або `authorId` наявного, або `name` нового, рівно одне з двох. Кандидатів показує інтерфейс (їх віддає той самий `/catalog/search` окремим полем `authorMatches`), а вибір робить людина. Мовчки звести двох людей в одну гірше, ніж лишити дублікат: дублікат видно й можна змерджити (§6.3), а зрощені автори втрачають межу назавжди.

### Що можна робити з примірником

`PATCH /me/library/:copyId` міняє `condition`, `note`, `visibility`, `acquiredAt` — і `status`, але лише між `AVAILABLE` та `UNAVAILABLE` (§4.5: «власник тимчасово не дає»).

- `RESERVED` і `LENT_OUT` клієнт передати не може **в принципі**: у схемі запиту стоїть звужений enum із двох значень, тож вони відпадають на валідації з 400, а не на бізнес-перевірці. Цими станами керує виключно стейт-машина §5.
- `COPY_STATUS_LOCKED` (409) спрацьовує **тільки якщо тіло містить `status`**, а книжка не вдома або має лоан у `APPROVED`/`HANDED_OVER`.
- Решта полів не блокується ніколи. Нотатка про стан книжки потрібна власнику саме тоді, коли її хтось тримає, а `visibility` ортогональна до `status` за §4.5.

Умова стоїть у самому `updateMany`, а не перевіркою перед ним: між читанням і записом лоан може змінити стан, і гонку мусить розвʼязати база — той самий оптимістичний прийом, що у `FriendsService`.

**Видалення** заблоковане, поки є лоан у `APPROVED` або `HANDED_OVER` (§5.2). Це не формальність: `Copy → Loan` каскадний, тож без заборони видалення примірника стерло б **історію позичань**, яка в цій моделі живе виключно в `Loan` (§4.6). Перевірка теж усередині `deleteMany`.

### Три проєкції примірника

Не одна схема з опційними полями, а три різні — і це не дублювання:

| Проєкція             | Кому                     | Що видно                                                                                                                |
| -------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `ownCopySchema`      | власнику                 | усе, включно з `note`, `acquiredAt`, `visibility`; плюс `activeLoan` і `pendingRequestCount`                            |
| `visibleCopySchema`  | гостю бібліотеки         | статус, стан, `isHome`, тримач — за §6.6; плюс `myActiveLoan` (**тільки свій** лоан), `canRequest` і `expectedReturnAt` |
| `borrowedCopySchema` | тому, у кого чужа книжка | статус, стан і **власник** — інакше нема кому вертати; плюс лоан, яким книжка сюди потрапила                            |

Контекст позичання підпорядкований тому самому правилу: гість бачить лише власний лоан, а `pendingRequestCount` (скільки ще людей у черзі) існує **тільки** у власника. `canRequest` — capability, обчислена **сервером**, а не здогад інтерфейсу. Навіщо ці поля взагалі — у розділі [Стан кнопки «Попросити»](#стан-кнопки-попросити).

§9 вимагає, щоб приватне **не віддавалося з API**, а не ховалося в UI, і єдиний надійний спосіб це гарантувати — щоб приватного поля не існувало у відповідній функції взагалі. Одна проєкція з прапорцями рано чи пізно віддала б нотатку не тому, кому слід. Це перевіряється двічі: unit-тестом маперів і e2e-тестом, який шукає заборонені ключі в **сирому** тілі відповіді (розібране схемою тіло сховало б витік, бо zod зрізає зайве).

Лічильники в чужій бібліотеці рахують лише видимі примірники: «×1», а не «×2», — інакше саме число казало б, що є ще одна книжка, яку від вас сховали.

### Групування за виданням

`GET /me/library` віддає групи («Шантарам ×3 · 2 вдома, 1 у Марка»), але окремі `Copy` лишаються поштучно всередині: у них різні стани, різні нотатки й різні майбутні лоани (§3). Групування — чиста функція `groupByEdition()` із проєкцією елемента ззовні, тож та сама логіка обслуговує всі три ролі, не знаючи про жодну з них.

Фільтр `lang` — це мова **видання**: `Translation.lang`, а для видання мовою оригіналу (`translationId = null`) — `Work.origLang`. Різниця не косметична: том англійською в оригіналі й том англійського перекладу з японської — різні речі на полиці.

### Видимість чужої бібліотеки

`GET /users/:id/library` проходить три різні перевірки, і жодну не можна пропустити:

1. `AccessService.roleOf()` — роль (`OWNER` / `FRIEND` / `OTHER` / `BLOCKED`);
2. `isVisibleTo(role, owner.libraryVisibility)` — доступ до сторінки взагалі;
3. `copyVisibleTo(role, libraryVisibility, copy.visibility)` — на кожен примірник, **найсуворіше з двох** (§9).

Заблокований отримує 403 `FRIENDSHIP_BLOCKED` навіть до `PUBLIC`-бібліотеки, закрита бібліотека — 403 `FORBIDDEN`. Примірники фільтруються в застосунку, а не SQL-умовою: правило §9 живе однією чистою функцією, і переписати його запитом означало б завести другу реалізацію тієї самої матриці. Обсяг тут — домашня полиця, не стрічка.

Це перший реальний споживач `AccessService.roleOf()` і чотирьох чистих функцій `visibility.ts`: до цього етапу вони викликалися лише з тестів.

### Валідація каталогу

- **ISBN-13** — з контрольною сумою (§11), а не «тринадцять цифр»: `isbn13` унікальний, і одна помилкова цифра назавжди займає чужий номер, бо редагування метаданих у v1 немає. Перевіряється й префікс Bookland (978/979) — інакше будь-який штрихкод із пляшки мінералки пройшов би, бо алгоритм суми в EAN-13 той самий.
- **Мови** — повний список 184 кодів ISO 639-1, а не `/^[a-z]{2}$/`: «zz» має відхилятися.
- Обидва правила живуть у `packages/shared` **функціями**, а декоратори `@IsIsbn13()` / `@IsLanguageCode()` у `apps/api` лише підключають їх. §11 вимагає два механізми валідації, але саме правило дублювати не можна: переписана вдруге контрольна сума розійшлася б із першою правкою, і тест парності цього б не побачив — він порівнює вироки, а не джерела.

Відома розбіжність механізмів, зафіксована тестами: **невідомі поля** zod зрізає, а `forbidNonWhitelisted` відхиляє весь запит. Обидва результати безпечні — зайве поле не доїжджає до Prisma в жодному разі.

## Позичання

### Ендпоінти

```
POST   /api/v1/loans                  { copyId, message?, proposedDueAt? }
GET    /api/v1/loans                  ?role=owner|borrower&status=…
GET    /api/v1/loans/:id
PATCH  /api/v1/loans/:id              { action: approve | reject | cancel |
                                                hand_over | return | mark_lost,
                                        note?, dueAt? }
```

Один `PATCH` із полем `action` замість шести маршрутів (§8): усі переходи проходять крізь одну точку, де живе валідація стейт-машини. Прямих ендпоінтів «підтвердити» чи «повернути» немає й не буде — кожен із них був би другим місцем, де ухвалюється рішення про перехід.

`dueAt` приймається **лише** разом із `approve`: термін повернення встановлює власник, погоджуючи запит. Правило про пару полів `class-validator` не виражає, тож воно живе в zod для фронту й перевіряється контролером — та сама навмисна розбіжність механізмів, що вже зафіксована для «оновити хоч щось» у `PATCH /me`.

### Стейт-машина

Рішення «чи можна» ухвалює **чиста** `resolveTransition()` у `loans/loan.transitions.ts`: ні Prisma, ні Nest, ні винятків HTTP. Це не стилістика — саме так правило §5 стає незламним. «Усі переходи через один сервіс» легко порушити наступним контролером; «рішення ухвалює функція без доступу до бази» порушити не можна, не переписавши той файл. Побічний ефект, заради якого це й робиться: уся таблиця §5.1 покривається unit-тестом без PostgreSQL — 84 комбінації «статус × дія × актор», перебрані вичерпно.

| Звідки        | Дія       | Хто                 | Куди          | Треба від `Copy`           | `Copy` після  | Тримач                     | Позначка      | Сповіщення                               |
| ------------- | --------- | ------------------- | ------------- | -------------------------- | ------------- | -------------------------- | ------------- | ---------------------------------------- |
| `REQUESTED`   | approve   | власник             | `APPROVED`    | `AVAILABLE`, удома         | `RESERVED`    | **не змінюється**          | `respondedAt` | `LOAN_APPROVED` + відхилення конкурентів |
| `REQUESTED`   | reject    | власник             | `REJECTED`    | —                          | не чіпається  | —                          | `respondedAt` | `LOAN_REJECTED`                          |
| `REQUESTED`   | cancel    | позичальник         | `CANCELLED`   | —                          | не чіпається  | —                          | —             | —                                        |
| `APPROVED`    | cancel    | **будь-хто з двох** | `CANCELLED`   | `RESERVED`, удома          | `AVAILABLE`   | —                          | —             | `LOAN_CANCELLED` другій стороні          |
| `APPROVED`    | hand_over | позичальник         | `HANDED_OVER` | `RESERVED`, удома          | `LENT_OUT`    | позичальник                | `handedAt`    | `LOAN_HANDED_OVER`                       |
| `HANDED_OVER` | return    | власник             | `RETURNED`    | `LENT_OUT`, у позичальника | `AVAILABLE`   | власник                    | `returnedAt`  | `LOAN_RETURNED`                          |
| `HANDED_OVER` | mark_lost | власник             | `LOST`        | `LENT_OUT`, у позичальника | `UNAVAILABLE` | **лишається позичальнику** | —             | —                                        |

Чотири рішення, які варто назвати вголос:

- **Підтвердження ≠ передача.** `APPROVED` не змінює `currentHolderId` (§5.2): книжка формально вдома, поки позичальник не натиснув «отримав». Без цього кроку статуси розсинхронізуються з реальністю в перший же тиждень.
- **`respondedAt` — це «власник відповів на запит»**, а не «востаннє щось сталося». Тому його ставлять лише `approve`, `reject` і авто-відхилення конкурентів. `REQUESTED → CANCELLED` лишає поле порожнім (відповіді не було), а `APPROVED → CANCELLED` **не перезаписує** значення від апруву. Окремих колонок під `CANCELLED` і `LOST` §4.6 не має, і вигадувати їх без вимоги специфікації не треба.
- **`reject` і `cancel` із `REQUESTED` не мають передумов на `Copy` і не чіпають його.** Власник міг після появи запиту перемкнути книжку в `UNAVAILABLE` — саме тоді прибрати висячий запит потрібно найбільше, і цей перехід не має права мовчки скасувати його рішення.
- **Дружба перевіряється лише на створенні.** Після появи лоану переходи авторизуються за `ownerId`/`borrowerId`. Це прямий наслідок §5.2: «видалення з друзів не скасовує активні лоани» — фізична книжка все одно в когось, і `return` мусить лишитися можливим. Повторна перевірка зробила б блокування інструментом утримання чужої речі.

### Конкурентність

Апрув — це транзакція, яка одночасно підтверджує один лоан і відхиляє решту, тож без блокування власник апрувне два запити з двох вкладок (§5.2).

**Блокування без небезпечного попереднього читання.** `PATCH /loans/:id` адресує лоан, а блокувати треба `Copy`. Читати `Loan` поза транзакцією, щоб дізнатися `copyId`, не можна: таке читання і неавторизоване, і застаріле до моменту запису. Тому перший запит транзакції одразу і знаходить рядок, і бере лок:

```sql
SELECT c."id" AS "copyId"
FROM "Loan" l JOIN "Copy" c ON c."id" = l."copyId"
WHERE l."id" = $1
FOR UPDATE OF c
```

**Після локу `Loan` і `Copy` перечитуються заново** — і це обовʼязково. `FOR UPDATE OF c` під EvalPlanQual освіжає лише **заблоковану** таблицю; рядок `Loan` лишився б зі снапшоту, взятого до очікування на локу, і той, хто програв гонку, побачив би свій запит ще `REQUESTED` замість уже відхиленого.

**Авто-відхилення конкурентів** не покладається на `count` від `updateMany`: він каже «скільки», а сповіщення адресні. Конкуренти спершу читаються (id + `borrowerId`), потім оновлюються з умовою `status = REQUESTED`, потім перечитуються — і `LOAN_REJECTED` іде рівно тим, чий рядок справді змінився. Розбіжність між прочитаним і зміненим означала б, що припущення про лок зламалося, і краще впасти, ніж мовчки недорахувати сповіщень.

**`P2002` мапиться тільки на своє обмеження.** `isUniqueViolationOn(error, 'one_active_loan_per_copy')` звіряє назву; будь-яке інше порушення унікальності летить далі незміненим — сховати його під `LOAN_ALREADY_APPROVED` означало б упевнено збрехати клієнту про причину. Prisma 7 працює через драйвер-адаптер і кладе назву **часткового** індексу не в `meta.target` (там поля), а в `meta.driverAdapterError.cause.originalMessage`. Форма версійно залежна, тож вона не припускається, а **пінується тестом на живій базі**: `test/db/loan-constraints.db-spec.ts` викликає реальне порушення й перевіряє, що функція його впізнає, а порушення `User_email_key` — ні.

**Логування — після коміту, не в callback'у транзакції.** Лог усередині стверджував би, що перехід відбувся, навіть коли транзакцію відкотили, і розслідування пішло б хибним слідом. Транзакція повертає metadata (`loanId`, `from`, `to`, `actorId`, відхилені конкуренти), а `logger.log()` викликається на її результаті.

Тестів на це три, і жоден не заміняє інші:

- `test/db/loan-concurrency.db-spec.ts` — сирі `pg`-сесії: чи справді `FOR UPDATE` ставить другу транзакцію в чергу і чи ловить індекс другий `APPROVED` без нього;
- `test/loans-concurrency.e2e-spec.ts` — та сама гонка **крізь `LoanService` і HTTP**;
- `test/loans-rollback.e2e-spec.ts` — атомарність §7.3.

Голого `Promise.all` для конкурентного тесту **замало**: він сподівається, що два запити перетнуться, а на швидкій машині вони спокійно виконаються один за одним — і тест зеленітиме, нічого не перевіривши. Тому гонка влаштовується примусово: окрема сесія тримає лок на `Copy`, обидва апруви гарантовано стають у чергу (це підтверджується опитуванням `pg_stat_activity`, а не `sleep`), і лише потім лок відпускається. Перевіряється рівно один `APPROVED`, усі інші `REQUESTED` → `REJECTED`, `Copy.status = RESERVED`, `currentHolderId = ownerId` і **рівно одне** сповіщення кожному позичальнику.

Програвший за коректного локу отримує `LOAN_INVALID_TRANSITION`: перечитавши лоан під локом, він бачить його вже відхиленим. `LOAN_ALREADY_APPROVED` лишається для випадку, коли спрацював індекс, — і саме тому він існує, хоч дійти до нього майже неможливо.

### Атомарність

§7.3, правило 1: запис `Notification` — у **тій самій** транзакції, що й перехід; відправка назовні — після коміту. Обіцянку «в одній транзакції» неможливо перевірити на успішному шляху, тож `loans-rollback.e2e-spec.ts` ламає запис сповіщення підміною `NotificationsService` і вимагає, щоб разом із ним відкотилося все: ані рядка `Loan`, ані зміненого `Copy`, ані частково відхилених конкурентів.

### `isOverdue` — прапорець, а не статус

§5.2: прострочення виводиться як `status = HANDED_OVER AND dueAt < now()`. Окремий статус довелося б проставляти по крону, і він завжди відставав би. Рахує це сервер, а не клієнт: інакше два пристрої з різними годинниками показували б різне про ту саму книжку.

`dueAt` — день без часу, як `Copy.acquiredAt`. У базі лежить **кінець доби** того дня: «до 12 червня» означає «12-те ще твоє». З опівніччю людина ставала б боржником зранку того самого дня, який сама ж і назвала.

### Стан кнопки «Попросити»

`Copy.status` на це питання не відповідає: за §5.1 створення запиту примірника **не змінює взагалі**, тож після надісланого прохання книжка лишається `AVAILABLE`. Інтерфейс, що вирішує за статусом, дозволив би натиснути вдруге й отримати 409 — помилку, яку клієнт мав знати наперед.

Тому проєкції примірника несуть контекст позичання, і джерела в них **різні**, бо різні й питання:

| Поле                  | Де              | Що означає                                                      |
| --------------------- | --------------- | --------------------------------------------------------------- |
| `canRequest`          | чужа бібліотека | **чи можна натиснути кнопку** — рахує сервер (див. нижче)       |
| `myActiveLoan`        | чужа бібліотека | незавершений лоан **того, хто дивиться**; чужої черги не видно  |
| `expectedReturnAt`    | чужа бібліотека | §6.5: орієнтовна дата повернення для `RESERVED` / `LENT_OUT`    |
| `activeLoan`          | своя бібліотека | єдина домовленість, що займає книжку (`APPROVED`/`HANDED_OVER`) |
| `pendingRequestCount` | своя бібліотека | скільки людей чекає у черзі — §5.2 дозволяє кілька              |
| `activeLoan`          | «чужі в мене»   | лоан, яким книжка сюди потрапила                                |

Один `activeLoanId` на всі випадки відповідав би не на те: на примірнику може висіти кілька `REQUESTED`, але ексклюзивний лоан завжди рівно один (§5.3.1).

**`canRequest` обчислює сервер, і це не зручність.** `/users/:id/library` віддає бібліотеку не лише другові: за §9 `PUBLIC`-полицю бачить будь-хто, а власник бачить свою завжди. Тому `status = AVAILABLE` не означає «кнопку можна малювати» — для стороннього вона дала б 403 `FORBIDDEN`, для власника 400 `LOAN_SELF`, а для того, хто вже попросив, 409 `LOAN_DUPLICATE_REQUEST`. Прапорець стає `true` лише коли виконано **все**: роль `FRIEND`, примірник видимий, `AVAILABLE`, книжка вдома, глядач не власник і не має власного незавершеного лоану на цей примірник.

Клієнт цього не перераховує: дружба й видимість — авторизаційні правила §9, і друга їх реалізація в браузері однаково не мала б потрібних даних, зате розійшлася б із першою. Кожен випадок (OWNER / FRIEND / OTHER / BLOCKED, повторний запит, зайнятий примірник) звірений e2e-тестом із реальним `POST /loans` — інакше передбачення розійшлося б із `LoanService` непомітно.

**`expectedReturnAt` — гола дата.** Ні `loanId`, ні позичальника, ні вкладених обʼєктів: поле відповідає на «коли книжка звільниться», а не «у кого вона». Тому `showHolderNames` до нього не застосовується — це факт про річ, а не про людину, — і тому це окреме поле, а не «лоан лише з потрібними полями».

### §5.3.2 — відхилення від еквівалентності

§5.3.2 записує інваріант як **еквівалентність**: `Copy.status = AVAILABLE ⟺ currentHolderId = ownerId`. Дослівно це суперечить власній таблиці §5.1 і §4.5 одразу двічі:

- `RESERVED` — «APPROVED не змінює `currentHolderId`» (§5.2), отже книжка вдома, а статус не `AVAILABLE`;
- `UNAVAILABLE` — «власник тимчасово не дає» (§4.5), книжка теж удома.

Обидва рядки — нормальні стани системи, тож еквівалентність не є її інваріантом. Реалізовано три імплікації, які §5.1 не суперечать:

```
status = AVAILABLE         ⟹ currentHolderId = ownerId
currentHolderId ≠ ownerId  ⟹ status ∈ {LENT_OUT, UNAVAILABLE}
status = LENT_OUT          ⟹ currentHolderId ≠ ownerId
```

Наслідок, який варто бачити: `RESERVED` не входить у множину другої імплікації, тож «домовлено» автоматично означає «ще вдома» — рівно те, чого вимагає §5.2.

**`UNAVAILABLE` навмисно двозначний** і саме тому не отримує третьої імплікації: він покриває і «книжка вдома, власник її не дає» (§4.5), і «книжка втрачена позичальником, тримач лишається ним» (§5.1, `HANDED_OVER → LOST`). Третій CHECK у стилі перших двох зробив би `LOST` неможливим.

Усі три вирази строго `TRUE` або `FALSE`: `status`, `currentHolderId` і `ownerId` — `NOT NULL`, тож NULL-пастка CHECK'а (через яку `friendship_block_author_valid` довелося писати через `CASE`) тут недосяжна.

### `NotificationType.LOAN_CANCELLED` — доповнення до §4.8

§5.1 для переходу `APPROVED → CANCELLED` вимагає «сповіщення другій стороні», але типу під нього в переліку §4.8 немає. Додано одне значення — адитивна зміна того ж класу, що вже задокументовані `Author.nameNorm` і `Friendship.blockedById`.

Переприсвоїти `LOAN_REJECTED` не можна: «вам відмовили» і «домовленість скасовано» — різні події, і на етапі 3 різниця поїде в текст листа та повідомлення в Telegram. Тип створюється **тільки** для `APPROVED → CANCELLED`; `REQUESTED → CANCELLED` і `HANDED_OVER → LOST` сповіщень не породжують — у §5.1 ці рядки мають порожню клітинку побічних ефектів, і це не пропуск.

## Історія та приватність

```
GET    /api/v1/copies/:id/history
GET    /api/v1/works/:id/history
GET    /api/v1/me/history
```

Історія виводиться з `Loan` — окремих таблиць немає (§4.6). Тому запис історії це не нова сутність, а **проєкція лоану для того, хто дивиться збоку**.

§9, рядок «Історія примірника з іменами»:

| Роль              | Доступ                       | Імена                |
| ----------------- | ---------------------------- | -------------------- |
| власник           | завжди                       | завжди               |
| друг (`ACCEPTED`) | за видимістю примірника (§9) | за `showHolderNames` |
| інший             | ✗                            | —                    |
| заблокований      | ✗                            | —                    |

Сторонній не бачить історії **навіть цілком публічного** примірника: видимість полиці й доступ до того, хто що в кого брав, — різні питання.

**Приватність — проєкцією, а не фільтром.** Проєкцій дві (`toNamedEntry` / `toAnonymousEntry`), як три проєкції `Copy`: §9 вимагає, щоб приватне не **віддавалося з API**, а не ховалося в UI, і єдиний надійний спосіб це гарантувати — щоб полів з іменами у відповідній функції не існувало взагалі. Одна схема з `.nullable()` рано чи пізно віддала б ім'я не тому: досить забути занулити одне вкладене поле.

Коли імена приховані, у відповіді немає **жодного** з: `owner`, `borrower`, `ownerId`, `borrowerId`, `currentHolderId`, `loanId`, `displayName`, `avatarUrl`. `loanId` прибрано навмисно — дій над чужим лоаном немає (`GET /loans/:id` віддасть 404), тож id був би рівно тим ідентифікатором, за яким два різні зрізи анонімної історії склеюються в одну людину. `historyCopySchema` теж не несе власника: чия це полиця, викликач знає зі сторінки, з якої прийшов.

Назовні це дискримінований union за полем `names`, тож клієнт звужує тип одним порівнянням і фізично не може прочитати ім'я там, де його немає. Перевіряється двічі: unit-тестом маперів і e2e-тестом, який шукає заборонені ключі в **сирому** тілі відповіді — розібране схемою тіло сховало б витік саме там, де його треба побачити.

`GET /me/history` завжди з іменами: viewer — сторона кожного з цих лоанів, а не стороння людина, і без імені йому немає кому вертати книжку.

## Сповіщення

```
GET    /api/v1/me/notifications           ?unread=true
PATCH  /api/v1/me/notifications/:id/read
POST   /api/v1/me/notifications/read-all
```

Створюються **тільки** рядки `Notification` (`IN_APP`-подія), у тій самій транзакції, що й зміна стану — §7.3, правило 1. `NotificationDelivery` навмисно не створюється: рядок доставки має сенс лише разом із воркером, який його забирає (§7.3, правило 2). Без диспетчера він назавжди лишиться `PENDING`, тобто таблиця черги брехатиме про свій стан. Диспетчер, канали (email, Telegram), ретраї й матриця `NotificationPreference` — етап 3 зі §14.

**`unreadCount` рахується завжди**, незалежно від фільтра: лічильник у навігації не має залежати від того, яку вкладку зараз відкрито.

**`?unread=` приймає рівно два рядки** — `true` і `false`. Ширші синоніми («1», «yes», «on») довелося б дослівно повторити в обох механізмах валідації (§11), і перша ж розбіжність пройшла б непоміченою. `ValidationPipe` тут із `enableImplicitConversion: false`, тож параметр приїжджає рядком; `@Transform` розпізнає два значення, а решта падає на `@IsBoolean()` з 400 — мовчазне зведення невідомого рядка до `false` показало б не той список і не сказало б про це.

**`markRead` ідемпотентний.** `updateMany` з умовою `readAt: null` тримає одноразовість запису, але його `count = 0` означає три різні речі: уже прочитане, неіснуюче або чуже. Тому після запису рядок перечитується за парою `{ id, userId }` — вона ж і фільтр власності, і джерело відповіді. Друга вкладка отримує 200, а чуже сповіщення — 404.

**`payload` читається без мовчазного фолбеку.** Колонка — `Json`, тож її форма нічим не гарантована. Невдала перевірка не валить список і не підставляє `{}` тихцем: у лог іде `warn` із id сповіщення та **шляхами** проблемних полів (не значеннями — там можуть бути чужі ідентифікатори), а назовні йде явний порожній fallback.

PostgreSQL 17 у Docker, Prisma 7 як ORM. Схема — `apps/api/prisma/schema.prisma`, джерело правди — §4 специфікації.

| Команда                       | Що робить                                                              |
| ----------------------------- | ---------------------------------------------------------------------- |
| `pnpm db:up` / `pnpm db:down` | підняти / зупинити PostgreSQL у Docker                                 |
| `pnpm db:generate`            | згенерувати Prisma Client                                              |
| `pnpm db:migrate`             | створити й застосувати міграцію за змінами схеми (dev)                 |
| `pnpm db:migrate:create`      | створити міграцію **без** застосування — для ручних правок SQL         |
| `pnpm db:deploy`              | застосувати наявні міграції (CI, прод, чиста локальна база)            |

### Тестова база

`pnpm test:db` працює не з dev-базою, а з окремою (`TEST_DATABASE_URL`), яку **дропає й створює заново на кожному прогоні**, після чого накатує міграції. Тобто кожен запуск заразом перевіряє, що чиста PostgreSQL приймає всю історію міграцій з нуля. Достатньо, щоб контейнер був піднятий — саму базу створить `test/db/global-setup.ts`.

> ⚠️ **`test:db` виконує `DROP DATABASE`.** Перед цим `test/db/guard.ts` робить **fail-closed** перевірку, і без неї жодного підключення не відбувається. Дропнути можна лише базу, яка:
>
> - має назву за шаблоном `^[A-Za-z0-9_]+_test$` — whitelist, тож лапки, пробіли, слеші й будь-які SQL-фрагменти не проходять за побудовою;
> - не є `postgres`, `template0` чи `template1`;
> - лежить на `localhost`, `127.0.0.1` або `::1` — віддалений хост заборонено завжди;
> - не збігається з `DATABASE_URL` або `DIRECT_DATABASE_URL` за нормалізованими host / port / назвою (петльові адреси зводяться до однієї, порт за замовчуванням добирається — щоб та сама база, записана іншим рядком, не проскочила).
>
> Будь-яке порушення — виняток, а не фолбек. Перевірка чиста й покрита unit-тестами в `test/db/guard.spec.ts`, які їдуть у `pnpm test` без PostgreSQL.

Jest тут запускається через `node --experimental-vm-modules`: Rust-free клієнт Prisma 7 підвантажує WASM-компілятор запитів динамічним `import()`, а той у пісочниці Jest без цього прапорця недоступний.

> ⚠️ **`--runInBand` замінено на `maxWorkers: 1` + `workerIdleMemoryLimit: 512MB`** (в обох конфігах, `test/jest-e2e.json` і `test/jest-db.json`). Виконання лишається послідовним — один воркер обробляє файли по черзі, — але воркер тепер окремий процес, який Jest перезапускає, коли той переростає ліміт.
>
> Причина не косметична. Кожен e2e-файл піднімає власний Nest-застосунок, а з ним `PrismaClient` і **окремий екземпляр WASM-компілятора запитів**. У `--runInBand` усе це накопичувалося в одному процесі, і починаючи приблизно з десятого файлу Node падав із `0xC0000409` — без повідомлення, без стеку, без жодного проваленого тесту. Відтворюваність рівно порогова: дев'ять файлів проходили завжди, десять не проходили жодного разу; кожен файл окремо теж проходив. Збільшення `--max-old-space-size` не допомагало, тобто це не звичайний OOM у купі JS. Перезапуск воркера звільняє накопичені WASM-екземпляри, і повний прогін стає стабільним.

### Правка міграцій руками

Дещо з §4.9 і §5.3 Prisma Schema Language не виражає, тож ці рядки дописані в `migration.sql` вручну:

```sql
-- на самий початок першої міграції
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;

-- у кінець першої міграції
CREATE UNIQUE INDEX one_active_loan_per_copy
  ON "Loan" ("copyId")
  WHERE status IN ('APPROVED', 'HANDED_OVER');

-- у кінець міграції friendship_block_author
ALTER TABLE "Friendship" ADD CONSTRAINT "friendship_ab_ordered"
  CHECK ("userAId" < "userBId");

-- у кінець міграції friendship_block_author_integrity
ALTER TABLE "Friendship" ADD CONSTRAINT "friendship_block_author_valid"
  CHECK (CASE WHEN "status" = 'BLOCKED'::"FriendshipStatus"
              THEN "blockedById" IS NOT NULL
                   AND ("blockedById" = "userAId" OR "blockedById" = "userBId")
              ELSE "blockedById" IS NULL END);

-- на початок міграції catalog_search_normalization
CREATE OR REPLACE FUNCTION bookswap_norm(text) RETURNS text
  LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE AS
$$
  SELECT lower(public.unaccent('public.unaccent'::regdictionary, $1))
$$;

-- у тій самій міграції: бекфіл МІЖ ADD COLUMN і SET NOT NULL
UPDATE "Author" SET "nameNorm" = bookswap_norm("name");

-- у кінець міграції loan_state_machine: інваріанти §5.3
ALTER TABLE "Loan" ADD CONSTRAINT "loan_borrower_not_owner"
  CHECK ("borrowerId" <> "ownerId");

ALTER TABLE "Copy" ADD CONSTRAINT "copy_available_is_home"
  CHECK ("status" <> 'AVAILABLE'::"CopyStatus" OR "currentHolderId" = "ownerId");

ALTER TABLE "Copy" ADD CONSTRAINT "copy_away_is_lent_or_unavailable"
  CHECK ("currentHolderId" = "ownerId"
         OR "status" IN ('LENT_OUT'::"CopyStatus", 'UNAVAILABLE'::"CopyStatus"));

ALTER TABLE "Copy" ADD CONSTRAINT "copy_lent_out_is_away"
  CHECK ("status" <> 'LENT_OUT'::"CopyStatus" OR "currentHolderId" <> "ownerId");
```

Три CHECK'и `Copy` — це §5.3.2 в **ослабленій** формі, і чому саме так, описано нижче: [§5.3.2 — відхилення від еквівалентності](#532--відхилення-від-еквівалентності). Інваріант §5.3.3 CHECK'ом не виражається взагалі — це твердження про дві таблиці одразу, а CHECK бачить лише один рядок; його тримає `LoanService`, а перевіряють integration-тести.

`bookswap_norm` — єдине визначення нормалізації (§4.4) на весь застосунок; чому воно в БД, а не в TypeScript, описано в розділі [Каталог і бібліотека](#нормалізація-живе-в-бд-а-не-в-typescript). `IMMUTABLE` тут чесний лише завдяки двоаргументному `unaccent` з явним `regdictionary`: одноаргументний залежить від `search_path`, тому має volatility `STABLE`, а `STABLE`-функцію не можна класти в індексний вираз.

Згенерований Prisma `ALTER TABLE "Author" ADD COLUMN "nameNorm" TEXT NOT NULL` розбито на три кроки руками: без бекфілу між `ADD COLUMN` і `SET NOT NULL` міграція падає на будь-якій непорожній таблиці — тобто всюди, де вже є каталог.

Чому `friendship_block_author_valid` виглядає саме так — у розділі [Дружба та видимість](#blockedbyid--відхилення-від-43).

Порядок критичний: GIN-індекси нижче в тому ж файлі використовують `gin_trgm_ops`, і на **чистій** базі вони впадуть, якщо розширення ще немає. Локально цього не видно — розширення в старій базі вже є, помилка проявиться при першому розгортанні на сервері. Саме тому job `database` у CI щоразу піднімає порожній контейнер.

Самі GIN-індекси у Prisma Schema **є** (`type: Gin, ops: raw("gin_trgm_ops")`), тож генеруються автоматично й не розходяться зі схемою. Поза її знанням лишаються `one_active_loan_per_copy`, два CHECK'и `Friendship`, чотири CHECK'и позичання (`loan_borrower_not_owner` і три `copy_*`) і функція `bookswap_norm`. Зовнішні ключі (включно з `Friendship_blockedById_fkey`) Prisma породжує сама — їх правити руками не треба. Перевірено `prisma migrate dev --create-only` після їхнього застосування: згенерована міграція порожня, тобто Prisma їх не бачить і дропнути не пропонує. Якщо колись увімкнути preview-фічу `partialIndexes`, для індексу це зміниться — тоді його треба буде або перенести в схему, або вичитувати кожну нову міграцію.

CHECK'и дублюють те, що вже тримає код (`normalizePair`, стейт-машина переходів), і це навмисно: код захищає від помилки в запиті, база — від запиту в обхід коду, тобто від міграції, скрипта чи seed'а, який колись напишуть похапцем. Що вони **існують**, стежить `test/db/schema-objects.db-spec.ts`; що вони **працюють** — два файли поруч:

| Файл                                        | Що перевіряє                                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `test/db/friendship-constraints.db-spec.ts` | `friendship_ab_ordered`, `friendship_block_author_valid` (§4.3, §5.3.5)                                      |
| `test/db/loan-constraints.db-spec.ts`       | `loan_borrower_not_owner` і три `copy_*` (§5.3.2, §5.3.4), плюс форма `P2002` для `one_active_loan_per_copy` |
| `test/db/loan-invariant.db-spec.ts`         | сам частковий унікальний індекс `one_active_loan_per_copy` (§5.3.1)                                          |

> ⚠️ `friendship_block_author_valid` — пастка для наступного етапу. Поки єдиний вихід зі стану `BLOCKED` — видалення рядка, і інваріант тримається сам. Якщо колись зʼявиться перехід `BLOCKED` → інший статус, він **зобовʼязаний** занулити `blockedById`, інакше впаде саме тут.

Робочий цикл для будь-якої зміни, яку Prisma не вміє висловити:

```bash
pnpm db:migrate:create --name <назва>   # згенерувати, але не застосовувати
# → дописати SQL руками в prisma/migrations/<ts>_<назва>/migration.sql
pnpm db:deploy                          # застосувати
```

### Чим Prisma 7 відрізняється від блоку в §4.1

§4.1 писався під Prisma 6 і прямо просить звірити його з фактичною версією. Розбіжності:

| §4.1                               | Prisma 7.9                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| `provider = "prisma-client-js"`    | deprecated → `prisma-client`, і `output` тепер обов'язковий                      |
| `binaryTargets` із `linux-arm64`   | поля немає: Rust-движок прибрано, нативних бінарників більше не існує            |
| `url` / `directUrl` у `datasource` | перенесені в `prisma.config.ts`; `directUrl` як поле видалено                    |
| `extensions = [pg_trgm, unaccent]` | preview `postgresqlExtensions` згорнуто → `CREATE EXTENSION` сирим SQL (як §4.9) |
| `.env` підвантажується сам         | більше ні — `prisma.config.ts` вантажить кореневий `.env` явно                   |
| вбудовані драйвери                 | обов'язковий драйвер-адаптер `@prisma/adapter-pg` поверх `pg`                    |

**ARM (§13.1) від цього не постраждав, а спростився.** Вимога `binaryTargets` існувала тільки тому, що query engine був нативним бінарником під конкретну платформу. У сімці його немає — клієнт це TypeScript плюс WASM, однаковий на x86 і ARM. Пропуск `binaryTargets`, який у шістці проявився б помилкою про відсутній engine вже на сервері, тут неможливий.

**Намір `directUrl` збережено, механізм інший.** Міграції беруть advisory lock, який не переживає transaction pooling PgBouncer'а, тож ходити вони мусять напряму. Розподіл такий:

- `DIRECT_DATABASE_URL` → `prisma.config.ts` → Prisma CLI: міграції, introspection, seed;
- `DATABASE_URL` → драйвер-адаптер у `PrismaService` → рантайм застосунку.

Локально це той самий рядок, у проді — різні.

## Що далі

Етапи зі §14 специфікації:

1. **Кістяк** ✅ — схема Prisma, auth і профіль, дружба, каталог із ручним створенням, особиста бібліотека й перегляд бібліотеки друга.
2. **Позичання** ✅ — стейт-машина §5 з транзакціями й тестом на конкурентний апрув, історія примірника й твору, in-app сповіщення, кнопка «Попросити» (§6.5). Позначка «у кого з друзів є цей примірник» на сторінці твору поки лишається історією твору («хто з друзів це читав»): вона відповідає на те саме питання «чи варто просити» і не потребує окремого запиту.
3. **Сповіщення назовні** — email, диспетчер із `NotificationDelivery` і ретраями, Telegram-бот, матриця `NotificationPreference`, щоденна задача для `LOAN_DUE_SOON` / `LOAN_OVERDUE`.
4. **Якість даних** — автозаповнення за ISBN (`GET /catalog/lookup`), мердж дублікатів, вішлист. Fuzzy-пошук уже є: без нього не працює крок 2 зі §6.3, тобто сам флоу додавання книжки. Мердж при цьому підготовлений — пошук уже виключає записи з проставленим `mergedIntoId`.
5. **Оцінки** — `Review`, `TranslationRating`, ранг перекладів із cold-start-правилом. `Translation` у контракті поки навмисно без `score` і `ratingAvg`: показувати «0.0» під кожним перекладом гірше, ніж не показувати нічого (§10.3).

Редагування метаданих каталогу (§6.3, «створює будь-хто; редагує автор запису та адмін») теж лишається попереду: етап 4 зі §14 має ендпоінти лише на створення й читання.

Ключове з домену, що не можна спрощувати: `Work → Translation → Edition → Copy` — чотири різні сутності, і **позичається завжди `Copy`**. Кількість примірників — це `COUNT` рядків `Copy`, а не поле `quantity`.
